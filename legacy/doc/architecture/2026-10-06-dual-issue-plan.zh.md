# EdRV32 顺序双发射改造计划

以 2026 年 10 月 6 日完成上板验证的单发射版本为基线，分阶段实现顺序双发射。第一版采用主执行通道加普通整数 ALU 通道，保留一套 LSU、DCache 和 MDU。持续性能提升需要同时覆盖前端供给、双译码、双执行和双提交。

基线标签为 `single-issue-board-20261006`。计划状态为待实施；本次保存基线和制定计划，不改变 RTL 功能。后续实现使用独立的 `codex/dual-issue` 开发分支，基线标签保持不动。

阶段一评估已完成，结果见 [双发射指令流评估和开源设计对照](2026-10-06-dual-issue-evaluation.zh.md)。第二通道仅 ALU 的限制用于初始验证；目标接口需支持 B 分支及任一槽选择共享 LSU，并评估寄存化的晚 ALU/条件分支。以下第一版保守规则不代表最终双发射能力上限。

双指令前端阶段已完成并与标量后端集成，49 次回归和 12 轮固定镜像 CoreMark 验证通过。64 位取指和双发射后端尚待实施，详见 [开发记录及复现入口](dual-issue-development.zh.md)。

## 当前结构和改造边界

| 当前结构 | 对双发射的影响 |
| --- | --- |
| IF1/IF2 每次返回 32 位指令块 | 能供应两个压缩指令，不能持续供应两个 32 位指令；缓冲只能吸收短期差异 |
| ALIGN 每周期形成一条指令 | 必须支持查看最多四个半字，并形成零、一或两条完整指令 |
| DECODE/EX 和后端 pipe 保存单条 payload | 扩展为有顺序关系的两个槽，处理单槽推进、保持和冲刷 |
| 寄存器堆 2R1W | 普通双 ALU 需要最多 4R2W，并定义双写和写回到读口的优先级 |
| 单 LSU，四项 Load Queue | 保留每周期最多一条访存发射，增加第二条指令不要求两份 Cache |
| 单 MDU 保护槽 | 第一版 MDU 单独发射，继续保留 token、年龄和提交授权 |
| 单退休和单 GPR 写口 | 扩展为每周期退休零、一或两条，不能让双执行长期受单提交限制 |

当前最差时序路径经过 DCache Tag RAM、命中路数据合并、Load Queue 旁路、EX 操作数选择和 ALU 大小比较。增加第二通道时，必须避免把第二组旁路选择和配对判断直接接在这条路径之后。

2026 年 9 月的八级架构文档中部分旁路和 MDU 描述早于当前优化。功能基线以标签下 RTL、对应测试和报告为准；继续遵守寄存边界、精确异常、epoch 和 COMMIT 副作用所有权规则。

## 第一版发射规则

A 槽始终是较老指令，B 槽始终是紧邻的较年轻指令。A 不可发射时不越过 A 发射 B，不搜索后面更远的指令，也不引入寄存器重命名。

第一阶段只允许 ALU 加 ALU。通过后增加 Load 加独立 ALU、Store 加独立 ALU。B 只执行普通整数 ALU，不包含分支、跳转、访存、MDU、CSR、fence、mret、wfi 或异常指令。控制流和特殊指令在 A 单独发射。

同组配对必须同时满足：

- A 的非零写目的寄存器不等于 B 的任何实际读源寄存器，即不存在 A 到 B 的 RAW。
- 两条指令不同时写同一个非零寄存器，即不存在 WAW。
- 两条指令对更老的在途生产者都满足当前配置的操作数就绪条件。
- 两条指令使用的执行资源和后端保存容量都可接收。
- 两条指令属于同一有效顺序路径，不跨预测跳转或异常边界。

立即数指令不能把没有使用的 rs2 编码误判为依赖；x0 不构成写依赖。A 读取、B 写入同一寄存器的 WAR 在操作数均于写回前捕获的前提下可以配对，无需机械禁止。

第一版不做 A 组合 ALU 结果到 B 组合 ALU 的同组直通。不能配对时只消费 A，B 保持原身份，下一周期成为队首。先保证顺序和时序，再根据实测决定是否增加配对种类。

扩展阶段允许独立 B 分支，并通过双槽年龄和预测元数据处理 redirect；共享 LSU 从 A 或 B 选择唯一请求。参考 EH1 评估 Load/MUL 到晚 ALU 或晚条件分支、ALU 到 Store 数据旁路。依赖指令先保存身份和操作数，结果到达后在后续寄存边界执行，不能在一条组合路径中串联两次运算。晚分支必须同时评估额外误预测修正延迟。

## 前端和执行结果保存

ALIGN 扩展完整指令边界识别和双解压，正确消费 16+16、16+32、32+16、32+32 四种组合。IF2 必须提供最多四个有效半字及对应错误、PC、epoch 和预测信息；不足以构成 B 时只形成 A。

在现有 32 位取指接口上先验证双指令消费和缓冲，然后依据供给不足统计决定是否扩展为 64 位 ICache 命中返回。64 位返回需处理行尾、跨行、非对齐指令和 ROM/uncached 路径，不能直接拼接两个独立响应，也不能假定改变 IP 字宽就完成前端改造。

较年轻 ALU 可能比同组 Load 更早完成。后端必须保存这条 ALU 的结果和完成状态，直到较老 Load 可提交；暂停期间不得重复执行、覆盖结果或重新分配 Load token。优先使用各 stage 中明确的寄存容量和有序双槽，不建立通用乱序调度器。

每条指令保留 PC、原始指令、指令长度、epoch、目的寄存器、异常信息以及 LSU/MDU token。生产者顺序判断必须同时考虑流水阶段和槽内年龄，不能只按通道号选择。新增顺序标识需要说明位宽、最大在途数量及回绕比较条件。

## 双提交和精确异常

先支持两条普通 ALU 的双退休、双写回，再支持较老 Load 加较年轻 ALU。Store 组合的双退休必须在 Store 所有权和接受条件验证后开放。

A 未完成时 B 不退休。A 发生异常时清除 B，并禁止 B 的寄存器写入及副作用。若 B 携带异常，允许完成 A 的合法提交后，在正确的指令边界处理 B，不能误撤销 A。第一版特殊指令串行化，使用完整的较老指令排空条件。

COMMIT 继续拥有架构 GPR、CSR、Store/MMIO 和 trap 的不可撤销操作。缓存 Load 可以提前查询，设备访问仍仅在最老可提交时启动。CSR 的 minstret 按实际退休条数增加；中断边界、mepc、分支冲刷和迟到响应必须按指令顺序处理。MDU token 的退休、授权和结果写回不能被当作额外的无条件第二写口。

## 分阶段实施和验收

| 阶段 | 改造和输出 | 进入下一阶段的条件 |
| --- | --- | --- |
| 一 仿真评估 | 已完成 O2/O3 热运行轨迹、九种配对能力、带宽/访存等待敏感性模型，以及 biRISC-V/EH1 源码对照 | 以评估记录为输入，模型假设和遗漏成本与结果一起保留 |
| 二 前端双指令 | IF2 查看窗口、ALIGN 双形成/解压、零/一/二条消费和队列保持；后端暂以单条消费验证 | 混合长度、跨块、背压、预测跳转、取指错误、kill/epoch 全部通过 |
| 三 ALU 双通道和双提交 | 双译码、4R2W、同组 RAW/WAW 检查、ALU 加 ALU、双槽保存、双退休；保留可选单发射配置 | 独立 ALU 流在稳态每周期退休两条；依赖流正确拆分；单发射配置匹配基线架构行为 |
| 四 共享资源和分支 | 单 LSU 从任一槽选择访存，增加 B 分支，拓展旁路和双槽有序完成；特殊指令继续串行 | 缓存命中/未命中、Load 错误、Store 接受、队列满、迟到响应、年轻结果保持和双槽 redirect 均正确 |
| 五 晚执行评估 | 评估 Load/MUL 到晚 ALU/条件分支，以及 ALU 到 Store 数据；框架稳定后评估共享 MUL 配对 | 依赖身份和 token 正确，较老异常抑制较年轻结果；计入晚分支的修正延迟，按收益决定保留 |
| 六 整核验证 | 与 ISA 参考执行对照有序退休轨迹，定向测试和随机指令覆盖双槽异常、IRQ、CSR、fence、mret、预测冲刷 | 寄存器、内存、异常 PC、CSR 结果一致；计数器按实际退休条数更新 |
| 七 性能和布线 | 同一固定 O2/O3 镜像做周期/CPI/配对率对照，PDS 100 MHz 综合布线，按需评估 64 位取指 | 功能通过，时序约束满足，频率与周期共同计算的性能优于基线，再安排上板 |

阶段一的退休指令流分析只能估计动态配对机会，不能视为真实双发射 CPI。执行时机变化会改变 Cache、队列、分支和背压行为；最终收益由完整 RTL 仿真确定。O2 和 O3 都要测，不能仅依据其中一种编译调度决定设计。

## 文件改造范围

| 文件组 | 责任 |
| --- | --- |
| `cpu/frontend/` 和对应 pipe | 指令供给、双指令边界识别、预测元数据、消费数和冲刷 |
| `cpu/decode/` 和 `pipe_decode_to_ex` | 双译码、配对选择、源操作数、生产者年龄和双槽驻留 |
| `cpu/datapath/edrv32_regfile.v` | 4R2W、x0、双写及写回到读口碰撞语义 |
| `cpu/execute/` 和 `pipe_ex_to_mem1` | 第二整数 ALU、两路结果、本地背压和完成保持 |
| `cpu/lsu/` 和后端 pipe | 单访存资源、Load/Store token、年轻 ALU 结果有序流动 |
| `cpu/commit/`、`cpu/csr/`、`cpu/control/` | 双退休、架构写回、异常与中断、冲刷、年龄和计数 |
| `cpu/core/`、源码清单和测试 | 双通道集成、单发射配置、性能观测和回归入口 |

执行、冒险和握手策略保留在对应 stage 内；pipe 只存 valid 和 payload，不创建包装握手策略的 `*_logic` 模块。各边界有本地寄存容量，禁止让 ready/accept 透明跨越多个 stage。

## 关键仿真项目和决策指标

定向测试覆盖同组 RAW/WAW、允许的 WAR、两个写口读旁路、x0、立即数伪依赖、B 保持后变成 A、半组提交、A/B 异常、中断边界和压缩指令异常 PC。访存测试覆盖队列所有权、token generation、Store/Load 顺序、相同地址部分写合并，以及冲刷后旧响应不污染新指令。

性能观测至少包含发射和退休零/一/二条的周期数、B 槽缺指令、RAW/WAW、执行资源冲突、后端容量、分支边界、Cache miss、Load-use 和 MDU 占用。仅增加仿真观测，不为气泡诊断另行要求上板固件。

布局布线分别查看寄存器读到操作数捕获、Load 返回到 ALU、配对判断到有效位、双提交到寄存器写口以及 kill/epoch 控制。最终按 `频率 / CPI` 比较相同程序的执行速度，不能只用 CPI 降幅宣布性能提升。

下一项实施工作是双槽 DECODE/EX、4R2W 和双提交；先定义槽顺序、配对规则和异常契约，保持已验证基线标签不变。
