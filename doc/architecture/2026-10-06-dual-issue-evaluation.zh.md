# EdRV32 双发射指令流评估和开源设计对照

当前单发射版本具备足够的双发射配对机会，适合进入实现阶段。第二槽仅支持整数 ALU 可作为初始验证范围；目标设计应支持第二槽分支和从任一槽选择一条访存进入共享 LSU，并评估 Load 或 MUL 消费者的晚执行。前端供给、双提交和旁路时序需要与第二执行通道一起改造。

## 评估范围和验证结果

源码基线为 `429b2717298e90559df12b7faab33e82893acc4d`，标签 `single-issue-board-20261006`。在虚拟机的隔离副本中运行观察用 Verilator testbench，功能 RTL 未修改，整个被仿真 RTL 树的 SHA256 与本地基线一致。

固定 O2/O3 镜像均为 GCC 15.2.0、10 次 CoreMark 迭代，各运行三轮。周期、退休指令数和 CRC 与保存的单发射结果一致。分析使用第二轮完整退休流，包含 PC、解压后的指令编码、压缩标志、操作类型、退休周期和地址字段。

| 指标 | O2 | O3 |
| --- | ---: | ---: |
| 基线实测仿真周期 | 3,487,221 | 3,523,737 |
| 基线实测退休指令 | 2,899,049 | 2,944,145 |
| 观察窗口退休记录 | 2,899,054 | 2,944,150 |
| 压缩指令占比 | 52.8173% | 53.1860% |
| 分支和跳转占比 | 21.0435% | 20.2664% |
| 平均指令长度 | 2.94365 字节 | 2.93628 字节 |

观察窗口采用已有 HPM 事件启停边界，比周期/退休 CSR 的测量窗口多 25 周期和 5 条统计管理指令。指令流完整性与该观察窗口的退休计数核对，不把两个边界混为一谈。

正确路径退休流不包含被冲刷的指令，也不等于真实双发射的执行时序。它用于分析依赖关系和配对种类；执行、预测和 Cache 时序变化仍需要双发射 RTL 验证。

## 相邻指令配对机会

下表从队首顺序扫描，能配对时消费两条，否则只消费较老一条。配对要求 PC 连续，使用真实源寄存器，忽略立即数编码中的伪源，x0 不构成写依赖。默认禁止同组 RAW/WAW，允许操作数先读取情况下的 WAR；晚执行策略仅对指定依赖放宽 RAW。

覆盖率为参与配对的指令数除以全部指令数，即 `2 × 配对组数 / 指令数`。这些是忽略在途等待的贪心统计，不是实测双发射率，也不是最优调度的证明。

| 配对能力逐步增加 | O2 覆盖率 | O3 覆盖率 |
| --- | ---: | ---: |
| 仅独立 ALU 加 ALU | 31.71% | 33.63% |
| A 为 ALU 或访存，B 为独立 ALU | 44.02% | 45.35% |
| 共享单 LSU，访存可以位于任一槽 | 45.56% | 46.41% |
| 再允许独立分支或跳转位于 B | 57.21% | 55.74% |
| 再加入 biRISC-V 式共享乘法资源配对矩阵 | 61.69% | 60.14% |
| 再允许 Load/MUL 到晚 ALU、ALU 到 Store 数据依赖 | 63.21% | 61.43% |
| 再允许 Load/MUL 到 B 条件分支的晚执行 | 72.77% | 70.85% |
| 再允许 A 条件分支沿顺序路径配独立 B ALU | 76.73% | 75.15% |

最后一项仅统计实际退休的顺序路径。硬件发射时尚不知道分支实际结果，必须根据预测、异常和冲刷管理 B；错误路径成本不能从这些退休记录中得到。

O2 动态相邻 RAW 包含 138,800 组 Load 到条件分支、90,720 组 MUL 到 ALU 和 203,236 组 ALU 到 ALU。O3 对应为 138,820、32,400 和 214,356。不同编译调度改变了配对相位，因此应同时测试 O2 和 O3。不能因单个 CoreMark 程序中某种配对较少，就永久去掉通用处理器需要的资源路由。

## 等待和带宽的抽象重放

另建顺序发射和顺序退休模型，包含寄存器结果就绪时间、最多八条未退休容量、一套每周期最多接收一条访存的 LSU、保持到退休的单 MDU 槽、四条指令的前端窗口，以及单/双退休宽度。

模型分别测试每周期 4 或 8 个有效指令字节、访存结果延迟 2/3/4 周期。ALU 和分支延迟为 1，低位 MUL 为 1，高位 MUL 为 3，DIV 为 34。晚消费者只在指定同组依赖中延后执行；其他较老未就绪操作数继续阻塞发射。

模型假设正确路径的完美预测，不计 ICache/DCache miss、错误路径取指、实际 stage ready 延迟、Store drain、MMIO 或物理时序。它不是 biRISC-V/EH1 的仿真，也不是将来 EdRV32 双发射的性能预测。

以下仅展示 8 字节供给、访存延迟 3 周期的一组敏感性结果：

| 抽象配置 | O2 模型周期 | O3 模型周期 |
| --- | ---: | ---: |
| 同模型的单发射 | 3,411,991 | 3,439,657 |
| 仅独立双 ALU | 3,042,944 | 3,048,118 |
| 主通道访存配独立 B ALU | 3,019,629 | 3,032,089 |
| 共享 LSU 任一槽访存 | 2,983,015 | 3,010,845 |
| 加 B 分支 | 2,837,090 | 2,875,742 |
| biRISC-V 式资源配对矩阵 | 2,837,090 | 2,817,422 |
| 加晚 ALU 和 Store 数据旁路 | 2,818,918 | 2,801,196 |
| 加晚条件分支 | 2,545,778 | 2,527,996 |

模型单发射周期已经与实际 RTL 不同，不能把表中的改进比例直接换算成板上 CoreMark 分数。O2 的乘法资源扩展增加了贪心配对机会，但在这组等待模型中没有增加周期收益，这说明不能用配对组数直接计算节省周期。

另测同组 WAW 的有序双写放宽后，贪心配对更多，但这组模型周期反而各增加 2,960。更多合法配对会改变后面的依赖相位，并不保证更快；第一版保留 WAW 拆分，后续有证据再扩展。

当前 32 位取指每周期至多提供四个有效字节。在全部字节有效、无错误路径和命中等待的理想情况下，按照当前指令长度，供给上限约为 O2 1.3589、O3 1.3623 条指令每周期。缓冲可支持短时双发射，但不能永久突破平均字节带宽。64 位 ICache 命中返回是目标前端的重要评估项，不等于立即把外部 AXI 或整个 Cache 存储器改成双端口。

重放模型已通过独立双 ALU、单提交限制、RAW/WAW、合法 WAR、单 LSU、32 位供给、晚 Load 消费者和条件分支策略的定向自检。

## biRISC-V 的可借鉴结构

对照源码提交 `6af9c4be5a0807d368eaad5e49af52322e31d073`。它采用两个整数执行通道、单 LSU、共享乘法资源和 4R2W 寄存器堆。B 槽除了 ALU，也可以选择分支、访存或乘法；资源矩阵禁止同组双 LSU 和双 MUL，DIV/CSR 只走主槽并受到额外阻塞。

发射逻辑先判断 A，再把 A 的写目的加入临时 scoreboard，随后判断 B。因此 B 不能绕过被阻塞的 A，也不能直接使用 A 当周期尚未完成的 ALU 结果。旁路按流水阶段和槽内顺序选择较新的生产者；主槽异常/冲刷会抑制年轻槽。

对我们的启示是共享资源按指令槽选择，不要把第二通道永久限制为 ALU，也无需复制 LSU/DCache。其取指和指令集没有我们的压缩指令边界问题，不能照搬前端。

## VeeR EH1 的可借鉴结构

对照源码提交 `d04b1c7ae675a63dc4307cacfd10547ec937b928`。EH1 支持 RV32IMC，具有双译码和双提交；每条执行通道都有早 ALU 和晚 ALU，仍共享一个访存流水线和乘法资源。其数据侧设计包含 DCCM 和非阻塞 Load，不能直接等同于我们的 DCache 加 Load Queue。

它并非简单地禁止全部同组 RAW。`non_block_case_d` 允许 Load/MUL 后的依赖 ALU 转到晚执行，另有 ALU 到 Store 数据的专用旁路。译码中的 ALU 类也包含条件分支，EX4 确实例化了晚 ALU 并处理分支预测修正，所以 Load 到条件分支的延后执行是源码能力，不只是对普通加法的推测。

与此同时，源码明确禁止同组双 LSU 和双 MUL。通道提交和写使能按年龄、异常及冲刷分别处理；非阻塞 Load 的迟到写回还有额外寄存器写路径，不应把它简化成普通 4R2W 即可完成的设计。

对我们的启示是保留顺序提交和唯一副作用所有者，在 stage 内增加带依赖身份的晚执行容量，而不是在一个周期内串联两个 ALU。晚分支会推迟结果确认和误预测修正，收益需要与冲刷深度一起验证。源码中连普通 ALU 到 ALU 的同组晚执行都被注释为性能不佳的选项，不能把所有 RAW 都无条件放开。

## 改造选择和推进顺序

| 能力 | 选择和理由 |
| --- | --- |
| 初始第二槽 ALU | 保留为验证阶段，先打通双槽有效位、双结果、4R2W 和双提交 |
| 第二槽分支 | 作为目标能力；CoreMark 约五分之一是控制流，开源实现已有完整支持，动态配对收益也明显 |
| 任一槽选择共享 LSU | 接口按此设计，首轮仍每周期最多一条访存，不复制 DCache |
| 共享 MUL 配对 | 在双槽框架稳定后扩展，结果/授权/token 不能误当作第三条无条件退休 |
| 晚 ALU 和晚条件分支 | 纳入架构评估；优先研究 Load/MUL 消费者，禁止直接串联两个组合 ALU |
| 同组双 LSU、双 MUL、通用乱序或重命名 | 第一版不引入；当前证据不足以承担对应资源和验证范围 |

建议依次实现双指令前端、独立双 ALU 与双提交、单 LSU 配对及 B 分支，再做寄存化的晚消费者原型。晚执行位置在 MEM1/MEM2 附近评估，保持当前两级访存接口和 token 所有权；不能把结果未就绪的指令当作已完成 ALU 向后传递。

第二槽分支需要独立的 PC/指令长度/预测元数据，双槽 redirect 年龄仲裁以及 A 异常对 B 的抑制。共享 LSU 要按槽携带访存顺序和完成信息。4R2W、旁路和双提交分别有明确的寄存边界，不允许形成新的跨多级 ready 链。

当前单发射 PDS Setup 裕量只有 0.434 ns，最差路径经过 Load 旁路到 ALU 比较。双通道增加的旁路扇出和选择层次需要早期综合评估；晚执行可缩短部分数据链，但也增加控制流确认延迟。实际时钟和资源占用必须由新 RTL 的布局布线得到，不能从开源核的 CoreMark/MHz 或 ASIC 目标频率推算。

## 可复现材料

`out/audit/2026-10-06-dual-issue-evaluation/` 保存观察 testbench 生成器、模型源码、自检入口、O2/O3 三轮日志、完整压缩退休轨迹、SHA256、开源源码提交及文件哈希、配对统计 CSV 和等待/带宽敏感性 CSV。

入口为 `prepare_trace.py`、`run_trace.py`、`run_analysis.py` 和 `summarize.py`。前面三个使用虚拟机中隔离的基线和固定镜像目录；`summarize.py` 在本机核对基线、轨迹和临时目录中的开源源码。参考源码只用于阅读，未复制到本核 RTL。
