## 2. 已经处于BIOS时，点击烧录仍等待重新进入BIOS

用户复现步骤：先按KEY1+复位进入BIOS，再点击调试工具烧录；工具不立即开始，必须再次按KEY1+复位，工具看到新一轮BIOS输出后才烧录。

代码机制已确认：tools/board/uart_tool.py的BiosTransfer.start把状态设为wait_menu；feed_line在active=False时直接返回；只有在wait_menu阶段新收到完整BIOS_MENU行才发送Program SRAM菜单选择。tools/debug_tool/core/engine.py的start_program仅调用program.start，没有把当前已显示的菜单状态传给传输器；tools/debug_tool/core/program.py启动提示仍要求按KEY1复位。

要求：板子已停在BIOS菜单时，点击烧录能直接开始，不能依赖捕捉进入BIOS的一瞬间，也不能要求用户重复复位。尚未进入BIOS时仍清楚提示如何进入。请Claude选择明确的当前状态确认/菜单交互方案；不要单凭很久以前的历史菜单就误向正在运行的应用发送二进制。

验收至少覆盖：先进入BIOS再点烧录；先点烧录再进入BIOS；同一次BIOS会话内再次加载；失败后界面状态可理解；原始.bin与已有ELF加载流程各自保持正确。记录原始UART会话和操作顺序。

## 4. 把项目定制功能集中为一个 SoC 中控台组件

用户要求：现有“场景、YOLO、视频”窗口可以合并；DDR与烧录也属于当前项目定制功能，应放到一个专用组件中，形成SoC中控台。中心区域统一显示板端回传的视频和图片，周围提供控制、传输、监测。

应整合的现有能力：
- 烧录/加载程序：现有SRAM bin和DDR ELF操作；显示当前BIOS/应用阶段、传输进度和结果。
- 场景控制：S1/S2、PIX、GEO、输出模式、fps、监控采样率；按当前工程能力显示适用功能。
- 图片发送与回传查看：共用文件入口和中心图像查看区域，保留现有YOLO图像检查需要的结果。
- 权重/模型发送：统一模型选择、发送进度和结果，B3VN/B3F适用；B3V明确不支持。
- 中央视频/图片显示：视频、静态图片和检测叠加在统一显示区切换，避免在不同窗口重复打开、重复配置接收。
- DDR观测：带宽、等待/利用率、异常计数及已有CSV导出，与场景/视频使用同一板级会话。
- 日志/状态：串口、烧录结果、模型/图片发送结果、回传状态能在同一工作流中查看，便于验收和导出证据。

目标是独立的项目专用组件/页面，使通用串口连接、命令、规则等功能与项目定制部分有清晰边界。请Claude统筹GUI和CLI/API共用会话；避免每页各自占用串口/UDP接收端或维护相互矛盾的板子状态。

上述是需求整理，不是已批准的详细UI布局或已经完成的功能。具体实现、协议调整和验证由Claude下发后续任务。
