# B1 上板准备与验证记录

## 1. 现象与范围

B1 需要可启动的 27 MHz → 100 MHz 板级顶层、无 C 的软件构建、PDS 存储初始化文件
和 Windows UART 下载工具。代码基于任务分支 `zc100116/task-board-b1`，已 cherry-pick
P1 `15d21f8`（本分支 `e5e97c6`）；功能实现为 `9a4c485`，最终板级/CPU B2/复位控制与 Spike 验证输入为 `921be55`
（后者只更新文档和仿真耗时打印）；较早单元回归的相关测试代码此后未改变。

集成时发现三处事实：make 输出是字节镜像而非任务背景描述的 64 位字镜像；系统
测试时钟仍固定为约 150 MHz；部分 UART/I2C 和 Spike 断言仍使用旧分频期望值。
另一次板级验证中，仿真输出通过，但验证期间提交改变了 HEAD，导致构建元数据比较
失败。软件构建最初还因 worktree 未初始化 CoreMark 子模块而缺少 `coremark.h`。

## 2. 复现与环境

先执行 `. ~/.local/opt/edrv32/env.sh`；工具为 Verilator 5.020、Icarus Verilog 12.0、
xPack GCC 15.2.0、Spike 1.1.1-dev。测试使用确定性激励，无随机种子选项。

```sh
git submodule update --init third_party/coremark
make -C sw PROGRAM=bootloader
make -C sw PROGRAM=monitor
python3 tools/fpga/mem_init.py build/sw/bootloader/rom.hex build/sw/monitor/sram.hex
make -C sw sys
python3 sw/tests/sys/run_spike.py
python3 sw/apps/monitor/run_spike.py
python3 tools/regress.py smoke --path verif/block/sys_cpu -j 1
python3 tools/regress.py smoke --path verif/block/sys_subsys -j 1
python3 tools/regress.py smoke --path verif/unit/periph_sysctrl -j 1
python3 tools/regress.py smoke --path verif/unit/periph_uart -j 1
python3 tools/regress.py smoke --path verif/unit/periph_i2c -j 1
python3 tools/regress.py smoke --path verif/unit/soc_reset_ctrl -j 1
python3 tools/regress.py smoke --path verif/block/cpu_b2 -j 1
python3 tools/regress.py smoke --path verif/soc/board_b1 -j 1
```

每条回归命令串行执行，未使用 `--parallel`。最终各目录结果在第 6 节。

## 3. 观察

- `tools/elf2mem.py` 生成每 token 一个字节、`@` 后为区内字节地址的文件。
  `edrv32_rom_boot` / `edrv32_ram_sram` 行为模型按 64 位字 `$readmemh`；旧 `sys_cpu`
  runner 自己从 ELF 打包，并不直接加载 make 的字节镜像。
- 原 `sys_cpu` bench 使用 `#3.333`，`sys_subsys` 的 `sys_half=3.333`；分频期望中有
  150000000、20833、93 等旧值。UART 模型仍使用真实 115200 8N1。
- 板级菜单场景实际输出五行 logo、`CLK_SYS_HZ: 100000000`、
  `ISA: rv32im_zicsr_zifencei`、`System info result: PASS` 和第二次菜单。
- 下载场景实际输出 `UART download ready`、`UART download complete`、
  `B1 UART application PASS`，并由软件写入 `SIM_EXIT=0`。
- 原始日志：`build/board_b1/{compile,case0,case1,bootloader,monitor}.log`，
  `build/sys_cpu/`、`build/sys/` 与 `build/regress/smoke/`。

## 4. 根因与协调结论

时钟常量、测试时钟和旧断言未使用同一来源。构建元数据不匹配则来自软件构建后
验证期间 HEAD 改变，实际 UART 数据中的旧提交号正确反映了软件编译时的输入。

协调者通过 ask 明确：

1. 不修改 `tools/elf2mem.py` 和其众多消费者；B1 工具读取字节格式，板级仿真共用
   `tools/fpga/mem_init.py` 的打包函数。
2. 不修改 `tools/cpu/`，其旧 C 扩展验证保留到 C-R9；生产软件、sys/monitor Spike
   和 `sys_cpu` ISA 检查去掉 C。最终 diff 中 `tools/cpu/` 无改动。
3. 显式约束 PLL 输出，并按厂商示例完整填满初始化文件；Windows 卡由协调者安排
   验证实际 IP 导入、初始化地址顺序与 PLL 时钟层次/周期。

## 5. 修复及交付

CPU 子系统和原 FPGA 测量顶层仅将 `RVC_EN` 默认值改为 0；没有修改 CPU、cache、
系统子系统的功能 RTL。生成时钟常量改为 100000000，测试时钟、分频与检查从该
常量推导。未修改 `docs/spec/`、`docs/plan/` 或 `rtl/filelists/`。

板级顶层例化真实 CPU/系统子系统和 `ip_pll_sys`，按键复位与 `lock` 共同送入既有
复位控制。UART、启动按键与 4 个 LED 的引脚/IO 属性和原测量顶层逐字一致；DDR
和媒体 APB 无目标的接法与原顶层一致。没有加入时序测量激励或观察寄存器。

### PDS 初始化格式及依据

只读厂商 demo 根目录：
`SOC系统设计/doc/fpga/pago_200/2_Demo/2_6_ram_rom_fifo/2_6_ram_rom_fifo/3_6_ram_rom_fifo/`。
`rom_test/rom_test/ipcore/rom_test/init_param_hex_exmp.dat` 注释明示“数据 64 bit、地址
10 bit、横向表示数据、纵向表示地址”，正文 1024 行、每行 16 个 HEX 字符；对应
BIN 示例是 1024 行 × 64 字符。`rom_test.idf` 实际选择 `INIT_EN=true`、
`INIT_FORMAT=HEX`、64 位、10 位地址，指向上一级无注释的示例文件。

转换器按小端把 8 个字节打包为 64 位字，从地址 0 递增输出无注释、无 `@` 的 HEX。
空洞与末尾补零，`build/fpga/ip_rom_boot.dat` 固定 2048 行，
`build/fpga/ip_ram_sram.dat` 固定 8192 行。demo 总是填满深度，未证实短文件语义；
本实现不依赖短文件语义。IP Compiler 选择 HEX 和对应 `.dat`，详见 `fpga/ip/`。
已逐字节比较转换内容与 make 从 ELF objcopy 得到的二进制，结果相同。

### PLL 时钟约束及依据

输入板钟周期 37.037 ns，D18；输出使用：

```tcl
create_generated_clock -name {clk_sys} -source [get_ports {clk_i}] [get_pins {u_pll_sys/clkout0}] -master_clock [get_clocks {clk_board}] -multiply_by {100} -divide_by {27}
```

显式语法依据厂商
`2_Demo/2_9_ddr3_test/2_9_ddr3_test/ddr3_test/ipcore/ddr3_test/pnr/ddr_test.fdc` 的 PLL
输出时钟约束。`2_5_pll_test` 工程没有 `.fdc`，未据此声称 PDS 自动推导。
Linux 未运行 PDS；综合网表中的准确层次、输出 10 ns 时钟与 IP 初始化导入均待
B1 Windows 卡实测，协调者已承接。

### 软件空间

GCC 15.2.0、`-O2`、`rv32im_zicsr_zifencei/ilp32`：

| 程序 | text | data | bss | section 合计 | 布局与容量 |
|---|---:|---:|---:|---:|---|
| bootloader | 4584 | 0 | 0 | 4584 | ROM 16384，剩余 11800 字节 |
| monitor | 19492 | 8 | 2116 | 21616 | SRAM 静态布局到 `0x10005484`（21636 字节），栈顶 `0x10010000` |

monitor 的文件镜像 19500 字节，小于下载上限 61440（64 KiB 减 bootloader 顶部 4 KiB
栈）。包含 BSS 与对齐的静态布局也小于 61440，还剩 39804 字节；到 SRAM 顶共有
43900 字节。这是链接布局/预留空间计算，未测量动态栈高水位。小下载程序二进制为
283 字节，导出的 UART 流 287 字节（4 字节长度 + 原始镜像）。

UART 工具使用 pyserial 3.5，输入是 ELF 经 objcopy 生成的 `.bin`；可输出仿真流，
也可在 Windows 等待 ready 后下载、持续显示并保存日志，并在菜单后发送选项 1/2/3。
使用方法见 `tools/board/README.md`。

此前首次 C++ 编译会增加总耗时；系统子系统既有 I2C/UART 组首次编译约 109/114 s，

系统 Spike 的 sys_spike/sc01/sc04 均到达 tohost=0；monitor Spike 的 1/10 次算法 CRC
和合成度量格式检查均 PASS。monitor 使用既有第三方源码的 `-Werror` 豁免，未改上游。

及 SIM_MODE，0 告警；板级与系统子系统各组实际编译亦启用 `-Wall` 并通过。
重现三个顶层 lint（每次独立执行，同一代码输入）：

```sh
python3 - <<'LINT'
from pathlib import Path
import subprocess
from tools.regress import expand_files
sources = expand_files(Path('verif/soc/board_b1/files.f'))
for top, extra in [
    ('edrv32_cpu_subsys', []),
    ('edrv32_fpga_cpu_sys_top', ['fpga/rtl/edrv32_fpga_cpu_sys_top.v']),
    ('edrv32_fpga_board_b1_top', []),
]:
    subprocess.run(['verilator', '--lint-only', '--timing', '-Wall',
                    '+define+SIM_MODE', '--top-module', top] + sources + extra, check=True)
LINT
```

原始 strict lint 日志：`build/board_b1/<顶层名>.lint.log`、`build/sys_cpu/lint.log`。
初始化两份文件的行数/行宽与每个 ELF 文件镜像字节已比较相同；UART 导出流也已
比较为精确的 4 字节小端长度 + 283 字节原始负载，随后经真实 UART 模型完成执行。

修改文件完整清单可由 `git diff --name-only e5e97c6^ HEAD` 重现，完成消息同时附带
逐文件清单。交付按事项拆分提交，未推送或合入 main；剩余工作仅为 B1 Windows
任务卡中的 PDS/IP/上板实测。
