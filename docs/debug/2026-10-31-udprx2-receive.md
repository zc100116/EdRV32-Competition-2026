# UDP 视频与 YOLO 接收剩余丢包

## 1. 现象

T-UDPRX 后仍未达到 30 fps 零丢帧；YOLO 缺包时接收路径报 ValueError，
共享 socket 关闭，文件夹无法继续。详细数字见
[测量报告](../reports/2026-11-01-perf-udprx.md)。

## 2. 复现

基线 `63a14aba`，独立进程及授权超时代码 `e7ef3642`。
按报告的 flock 命令运行 stress_test.py 与单元测试，使用现有工具依赖。
VM 测量中发送端与接收端在同一台机器、不同进程，走 UDP 回环；GUI 为 offscreen。
请求 64 MiB SO_RCVBUF，接收端实际读回 **425984 B**。

## 3. 观察

静置 socket 的 400 个 1032 B 数据报只排入 185 个，400 包可装入的前提不成立。
uniform 的绝对 deadline 追赶会在发送进程暂停后压缩间隔；修正为最小间隔后，
VM 实际发送帧率低于 29.5，因此不能用它验证 30 fps 接收能力。
最终完整 720p 突发：源 29.989 fps，接收 18.993 fps，284 丢弃帧，
194262 丢失包，接收进程 CPU 48.42%。
分段补测（脚本 d08de055）：成功看到帧头的 880 帧中，269 帧不完整；
前 / 中 / 后各 600 包分别缺 39167 / 66676 / 44360 包，中段最多（44.4%），
前后段也缺；这是逐帧位图的聚合，不意味着每帧都主要丢在中段。
20 批未见帧头，无法用该方法定位；详细分母与该次性能数字见报告。

## 4. 已确认的根因与证据边界

Linux 缓冲计入 skb 开销，425984 B 不能缓存完整 400 包或 720p 突发。
独立进程不会扩大内核队列；现有数据不能证明剩余损失全部只来自缓冲上限。
原 YoloTool.receive 在 EDDT 已到、图像缺包时抛 ValueError，
EthernetTool._receive 的错误退出路径随之关闭整个共享 socket。
若最后 EDDT / NOTIFY 丢失，协议本身没有可判定结束的信息。

## 5. 修复

视频与 YOLO 逐包接收、组帧移入 spawn 进程，共享内存交付完整帧；
主进程保留独立只读快照，EDDT / EDTM / 文件处理维持原用途。
YOLO 有结束但缺包按单张失败，日志列出窗口和缺失字节，队列继续。
经协调者明确授权，缺结束从最后回传包起 1 s 超时；无回传包从图像发送完成起算。
最终 YOLO 30 张完整 16、失败 14、未结束 0；没有放宽完整性规则。

## 6. 防回归

101 项测试通过，覆盖缺包后正常下一张、失败计数、队列推进、
持续 EDTM 下缺结束超时、无包从发送完成起算、共享槽重用与停止回收。
视频性能目标仍 failed，不能以单元测试通过替代性能验收。

## 7. 同类排查

共享监听器、EDDT 检测、EDTM 遥测、普通文件路径均经回归；
magic / 版本等协议错误仍明确停止。未修改 DDR 监控和布局。
Windows 上板须记录 SO_RCVBUF 实际值；线速突发要求至少 2 MiB，Linux 另计 skb 开销。
