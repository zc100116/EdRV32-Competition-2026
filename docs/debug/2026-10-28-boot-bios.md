# B1-8：Boot ROM BIOS 与 SRAM 应用复位初始化

## 1. 现象

B1 上板后，更换 SRAM 程序需要重新生成 bitstream；旧 bootloader 的按键和
SCRATCH0 路径只支持 UART 下载后立即跳转，不能停留在 ROM 中烧录后按复位运行。
原 SRAM/DDR 链接脚本的 `.data` LMA=VMA，通用启动代码虽有复制循环，实际只是自拷贝，
无法在全局变量被改写后恢复初值。SoC 规格 v0.14 第 7.5(3、3a、3b) 已确认新行为。

## 2. 复现与实现版本

基点 `33d3bf8`，分支 `zc100116/task-boot-bios`；按事项提交：

- `da98fa6`：BSP SRAM/DDR 的 `.data` 初值副本与运行区分离。
- `b027c4d`：BIOS、100 ms KEY1 采样、共用行解析、删除启动方式交接。
- `d496086`：主机 UART 工具改用 BIOS 菜单。
- `1638cbc`：板级两次复位、SC 下载更新、共用窗口加速与真实计时 full 测试。
- `3a96a93`：可移植 `-O3 -flto=1` 模型构建与 UART 文档更新。
- `58f64e6`：初值副本按数据对齐，升级 32 字节对齐 uint64 复位负载。

工具：xPack GCC 15.2.0，Verilator 5.020（Debian 5.020-1），Spike 1.1.1-dev。
仿真固定无随机激励；板级 27 MHz 参考钟、100 MHz clk_sys，UART 真实 115200 8N1。
所有回归 `-j 1`，未用 `--parallel`，同一时刻只运行一个仿真。

## 3. 观察

板级烧录后的两个独立 `rst_n_i` 复位均输出：

```text
B1 data hi/lo: 7/7 bss: 0
B1 UART application PASS
```

小程序使用 32 字节对齐的 64 位全局变量（初值 `0x0000000700000007`），分别打印
高/低半字；每次输出初值后把 `.data` 变量改为 9、`.bss` 变量改为 3，调用
`cache_clean_all()` 将修改写到 SRAM 再写 SIM_EXIT，因此第二次运行确实需要恢复
初值并清 BSS。下载阶段检查 BIOS 标题、菜单、ready、十进制长度、PASS 和返回菜单，
直到按键松开再复位才允许应用运行。菜单选择使用 CR LF，覆盖文本/二进制边界。

## 4. 根因

旧流程与新规格不符；旧 `.data` 的加载地址和运行地址相同，变量修改覆盖了所谓的
初值。另一个边界是复用 monitor 的 CR LF 解析时，不能把二进制长度首字节 `0x0a`
当作菜单 CR 后的 LF。协调者确认主机必须等完整 ready 行后才发送长度，因此可在
ready 发送完成后消费已经排在 RX 中的菜单 LF，再以原始 UART 接收二进制。

## 5. 修复

- `BOOT_BUTTON_WINDOW_MS=100`：打印系统信息后读 SCRATCH0 并清零，以 CLINT
  `mtime` 与 SYSCTRL `CLK_SYS_HZ` 计算窗口，窗口内反复读 GPIO bit0，并累计是否松开。
  只在全程按下或 magic 请求时进入 BIOS。
- BIOS 只有 Program SRAM 一项，严格使用规格提示文字；长度只检查
  `1..EDRV32_SRAM_SIZE-4096`。收完调用 BSP `cache_clean_all()`，该接口发送
  CLEAN_ALL 并等待 BUSY 清零，再打印字节数/PASS 并回菜单。
- 行输入放在 `sw/drivers/uart_input.c`，状态由调用方栈持有；bootloader 无可变静态
  数据，私有启动代码只设置 GP/SP，保留 SRAM 应用。monitor 共用相同行解析。
- 删除 SCRATCH1 启动方式交接、`system_info(boot_mode)` 参数和 Boot mode 输出。
- SRAM/DDR `.data`：LMA 为 text/rodata 后按 `MAX(4, ALIGNOF(.data))` 对齐的地址，
  `.data` 结尾也按此对齐，VMA=LMA+SIZEOF(.data)，运行区随后分配 BSS。原 BSP
  启动复制和清零循环已正确，
  每次入口都执行。ROM 已使用 `> SRAM AT> ROM`，无需改布局。
- `elf2mem.py` 已按 PT_LOAD 的 `p_paddr` 加载，objcopy 也按 LMA 生成二进制，无需修改。

B1 monitor：text/data/bss=20388/8/2116 字节，`.bin`=20396 字节；
`.data` LMA=`0x10004fa4`，VMA=`0x10004fac`，BSS 结束=`0x10005804`，
SRAM 分配范围 22532 字节，栈顶=`0x10010000`。bootloader=5348/0/0 字节，
占 16384 字节 ROM 的 32.6%。构建日志在 `build/bios/` 与 `build/board_b1/`。

### 数据对齐补查

补查 `uint64_t` 初值时发现，只有 4 字节对齐的镜像起点/结尾会使 `.data` 内部填充
改变 SIZEOF：原测试程序 text 结束 `0x100000b4`，LMA=`0x100000b4`，
VMA=`0x100000bc`，最终 size=12，两个范围重叠 4 字节。启动复制第一字会覆盖
后续尚未读出的初值。修复后统一按 `MAX(4, ALIGNOF(.data))` 对齐起点/结尾，
同一 uint64 程序 LMA=`0x100000b8`，VMA=`0x100000c0`，size=8，互不重叠。
板级负载升级为 32 字节对齐的 uint64 初值，以实际两次复位覆盖此问题；其 LMA
为 `0x10000240`，VMA=`0x10000260`，section size=32。

对齐修复及 64 位/32 字节对齐负载的提交：`58f64e6`。此前 SC 测试程序的 `.data`
均为无初值段或至多 4 字节对齐，monitor 的 `.data` LMA/VMA 也保持原值；对齐修复的
补充验证使用增强板级负载与 SRAM/DDR 的 uint64 Spike 程序。
