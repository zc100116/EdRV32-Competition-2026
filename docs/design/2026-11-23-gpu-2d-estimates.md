## 1. 一帧画面怎么画出来

```
CPU：游戏逻辑 → 更新精灵表（DDR 中，每个精灵 8 字节）→ 写帧描述符 → START
                                         │
渲染器（片上）：
  ① 背景：图块地图层 1、2 → 逐像素铺满片上帧缓存（同时完成清屏）
  ② 精灵：DMA 读精灵表 → 逐个精灵：裁剪 → 按行展开 → 取素材像素 → 调色板/翻转
          → 颜色键/Alpha → 读改写片上帧缓存
  ③ 输出：整帧从片上拷到 DDR 的显示缓冲（一次顺序写）
                                         │
DISP：在 VSYNC 时翻页，从 DDR 读，整数倍放大到 1280×720 输出
```

- 帧缓存在片上，显示缓冲在 DDR，共两块。渲染第 N+1 帧时，显示的是第 N 帧，延迟一帧。
- 一帧里，DDR 只有三类访问：读精灵表、读背景图块地图（也可以放在片上）、写出整帧，都是顺序的大块传输。

## 2. 三个核心部件

### 2.1 低分辨率片上帧缓存

| 内部分辨率 | 放大 | RGB565 帧缓存 | 占 DRM（每块 36 Kb = 4,608 B） |
|---|---|---|---|
| 640×360 | 2 倍 | 460,800 B | 100 块 |
| 320×180 | 4 倍 | 115,200 B | 25 块 |

PG2L200H 共 415 块 DRM。

**为什么片上快**：

| | DDR 帧缓存（RND、千影） | 片上帧缓存 |
|---|---|---|
| 半透明像素 | 读目标要等 DDR 延迟，几十拍；写要凑突发 | 双口 RAM，一个口读，一个口写，每拍都能读改写 |
| 小精灵 | 每行几十字节，突发很短，效率低 | 任意地址，没有突发开销 |
| 与 CPU、显示的争用 | 共用 DDR 带宽 | 互不影响 |

**每拍画 4 个像素**：
- 片上 RAM 按 64 位宽组织，一个字存 4 个水平相邻的 RGB565 像素，写入时按像素使能。
- 精灵的一行是一段水平的像素，正好可以 4 个一组读改写。
- 起点不对齐时，用一级移位对齐，首尾两个字用像素使能屏蔽。

**连续写同一个字**：精灵重叠时，后一次读到的必须是前一次刚写的值。流水线中要加旁路（转发）。这是本模块唯一要仔细处理的冒险。

### 2.2 硬件精灵表

CPU 不再一个精灵发一条命令，只维护一张表。每项 8 字节，下表只是举例，字段由规格定：

| 字段 | 位宽 | 说明 |
|---|---|---|
| x、y | 11 + 10 | 有符号，可以部分移出屏幕，由硬件裁剪 |
| 图块号 | 12 | 素材库中的第几块 |
| 尺寸 | 2 | 8、16、32、64 |
| 调色板号 | 4 | 同一张素材换调色板，就能得到受击闪白、不同颜色的敌人 |
| 水平、垂直翻转 | 2 | |
| Alpha | 4 | 16 档透明度；0 表示只用颜色键 |
| 层、优先级 | 3 | 决定画的先后 |

- **画的顺序**：按表的顺序，后画的盖住先画的。
- **2.5D 遮挡**：需要按 y 坐标排序时，可以由硬件按 y 做桶排序，CPU 不必每帧对上万个精灵排序。是否做，待定。
- **读表开销**：1 万个精灵的表是 80 KB，DMA 以每拍 16 字节读入，约 5,000 拍，只占一帧预算的 0.2%。

### 2.3 图块地图与素材库

**素材用调色板索引色**（像素风的传统做法）：

| 格式 | 每个 16×16 图块 | 128 KB 能放 |
|---|---|---|
| 4 位索引（16 色） | 128 B | 1,024 块 |
| 8 位索引（256 色） | 256 B | 512 块 |
| RGB565 | 512 B | 256 块 |

- 素材库放在片上，取素材像素是固定的 1–2 拍，不会因为访存而停顿。
- 世界很大、素材放不下时，按关卡或区域从 DDR 换入。

**图块地图背景**：
- 地图是一张图块编号表，每项 16 位：图块号、调色板、翻转。
- 卷屏只改一个偏移量；地图做成 256×256 个图块，就是 4096×4096 像素的世界。
- 每层逐像素铺满屏幕一次。640×360 每拍 4 像素，需要 57,600 拍，约 0.4 ms。
- 第一层不透明，顺便完成了清屏。

## 3. 能力估算

**条件**：
- 渲染时钟 150 MHz，每帧 2,500,000 拍（60 fps）；
- 内部分辨率 640×360；
- 两层背景约 115,000 拍，输出到 DDR 约 50,000 拍（460 KB；按渲染器分到 1.4 GB/s 计约 0.33 ms），合计约 165,000 拍；
- 剩下约 2,330,000 拍画精灵。

**每个 16×16 精灵要多少拍**：
- 16 行，每行看起点是否对齐，平均占 W 个字；
- 每拍 4 像素时，一行占 4 或 5 个字，平均 4.75。

| 每拍像素 | 每行平均拍数 | 每个精灵拍数 | 每帧精灵数上限（60 fps） |
|---|---|---|---|
| 1 | 16 | 256 | 约 9,100 |
| 2 | 8.5 | 136 | 约 17,100 |
| 4 | 4.75 | 76 | 约 30,600 |

半透明（Alpha）不额外花时间：片上读改写本来就每拍完成。

**和千影比**：
- 千影是 640×480、DDR 帧缓存，2300 个目标跑 60 fps；
- 我们按每拍 4 像素，硬件上限约 3 万个，高一个数量级以上。
- 这个上限只算渲染器。下一节说明，真正先到上限的是 CPU。

## 4. 真正的瓶颈会转到 CPU

**估算**：
- 千影的 V85 版本，游戏逻辑段 2,426 µs 处理约 2,261 个对象，即每个对象约 1.07 µs，在 200 MHz 下约 215 拍。
- 按同样的代价，我们 125 MHz 的 CPU 处理 1 万个对象需要 2,150,000 拍，约 17 ms，已经超过一帧（16.7 ms）。
- 所以超过约 5,000 个对象后，瓶颈是 CPU 的游戏逻辑，而不是画图。

**可选的专门做法：硬件对象运动**：
- 弹幕游戏里，子弹、粒子的运动是公式化的。
- 给这类对象在表中增加速度、加速度、寿命字段；渲染器读表时顺便更新位置（位置 += 速度），寿命到了就自动失效。
- 硬件还可以检测子弹和玩家碰撞框的碰撞，返回命中列表。
- 这样 CPU 只负责敌人行为和游戏规则，数万颗子弹完全由硬件推进。
- 这是千影没有的部分，也是这个学习项目里最有意思的“专门算法”之一。是否做，作为待定项。

## 5. 为什么不用“按行合成”（老式游戏机的做法）

| | 按行合成（不要帧缓存） | 片上帧缓存（推荐） |
|---|---|---|
| 存储 | 只要两行的缓冲，最省 | 一整帧 |
| 精灵上限 | 每一行有上限，同一行精灵太多就闪烁或丢失 | 只受每帧总像素量限制 |
| 每行要找出覆盖它的精灵 | 上万个精灵时，每行都要扫表或预先分组 | 不需要，按精灵顺序画 |
| 3D 三角形和深度缓存 | 很难 | 直接画进同一块帧缓存，再加一块深度缓存 |

R1 定了要做 3D，所以选片上帧缓存。

## 6. 第二步 3D 如何接入

- 同一块片上帧缓存，再加一块 16 位深度缓存：640×360 占 100 块 DRM，320×180 占 25 块。
- 新增单元：
  - 顶点变换：定点 4×4 矩阵乘和透视除法；
  - 三角形光栅化：用边函数判断像素是否在三角形内，并插值纹理坐标和深度；
  - 纹理取样：复用 2D 的素材库。
- 2D 精灵和 3D 三角形共用帧缓存的读改写流水，所以 HUD、粒子可以直接叠在 3D 画面上。
- 具体规格在 2D 完成后再讨论。

## 7. 资源和风险

| 项 | 估算或说明 |
|---|---|
| DRM | 640×360：帧缓存 100 块 + 素材库 128 KB 约 28 块 + 深度缓存 100 块（3D 阶段），约 230 块，要求新 SoC 去掉 NPU 等大户；320×180 只要约 80 块 |
| 片上读改写旁路 | 重叠精灵连续写同一个字，必须转发，是 2D 流水线的主要验证点 |
| CPU 瓶颈 | 见第 4 节 |
| 素材容量 | 大世界要按区域换入素材 |
| 过载 | 一帧画不完时会掉帧，帧率直接显示在 HUD 上，不做降级 |
