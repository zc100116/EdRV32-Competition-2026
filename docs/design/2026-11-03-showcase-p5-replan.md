## 1. 背景和问题

卡 53 用 b3 d54b69f4 的 showcase-p4.elf 上板，验收没有通过。用户的反馈：

- 识别 3 fps，NPU 每帧 41.1 ms，后处理 177.1 ms（目标 ≤ 35 ms）；
- 虚拟输入仍然走串口，延迟大，鼠标乱跳，还会自动点击；
- 游戏中按 Esc 直接退回首页；
- 批量图片识别暂停后，实时识别和图像处理都失效了；
- 图像处理页没有逐项启用开关；
- 按钮高亮不消失，控件用法不对，页面不美观。

用户要求先重新规划，再下发实现卡和测试卡。规划要覆盖：

- 应用的生命周期，以及硬件资源归谁所有；
- 任务调度和预算；
- PC 工具与板端的状态同步；
- 图片改为手动逐张识别；
- 测量识别耗时，并拆分到各个阶段；
- LVGL 控件和输入。

## 2. 根因分析

下表的"依据"列中，"代码"表示已经在 d54b69f4 源码上确认，"推测"表示需要卡 54 实测验证。

| # | 现象 | 根因 | 依据 |
|---|---|---|---|
| R1 | 后处理 177 ms。画面里 0 个目标时也是这么慢，说明慢的不是 NMS | `vision.c` 用**不经过 cache 的地址**读 NPU 输出（注释写着"no full-buffer invalidation step"）。YOLOv8n 解码要扫 8400 个 anchor × 80 类，加上框的分布，约 69 万次逐字节的 DDR 读。独立的 demo_npu 先 `engine_dma_invalidate`，再按 cache 读（`demo_npu/inference.c:78`）。估算：177 ms × 125 MHz ≈ 2.2×10⁷ 周期，除以 6.9×10⁵ 次读，约 32 周期/次，与一次不经 cache 的 DDR 读的延迟相符 | 代码 + 估算 |
| R2 | 虚拟输入走串口 | 工具只通过串口上的 `ETH peer IP/port` 两行来确认 PEER（`session.py:100`）。板端只在 PEER **变化**时打印这两行，CPU 报告期间还把打印预算设为 0（`network.c`）。工具重连以后，板端的 PEER 没有变，所以不会再打印，工具也就一直等不到。结果是：工具每 2 s 发一次连接请求（日志中共 495 次），始终是 PEER=false，虚拟输入一直走串口，每 20 ms 发一帧。网口本身是通的：遥测和视频都在持续回传 | 代码 + 日志 |
| R3 | 鼠标乱跳、自动点击 | 主要嫌疑是串口回退路径：串口帧与网口状态帧混用；LVGL 的键盘设备把"任意键按住"都当作按下（`read_keys`）；页面切换后，按住的状态被下一个页面接收 | 推测 |
| R4 | 游戏中 Esc 回到首页 | 一次按键被处理了两次：<br>1. NES 收到 Esc 的按下沿，调用 `app_return`，主循环执行 `ui_game_open=false; ui_open(5)`，此时已经回到游戏列表；<br>2. GUI 恢复后，LVGL 的键盘设备读到 Esc 仍然按着，又生成一次 `LV_KEY_ESC`；`ui_back()` 看到 `ui_game_open` 已经是 false，于是执行 `ui_open(0)`，回到首页 | 代码 |
| R5 | 暂停后其他功能失效 | 三个视觉应用共用一个 `v` 状态，靠 `paused / waiting / reconfigure / camera_source / capture / job / image_pending` 七个标志组合出状态。`batch_stop` 只改了 `waiting` 和计数，工具仍在继续发图；而且没有"取消完成"的确认。卡 53 没有复现出具体的失败路径；结构上的原因是没有状态机，停止和恢复的条件散落在各处 | 代码（具体路径待复现） |
| R6 | 图片往返时间被量化到整秒 | 工具日志中，"回传完整"总是落在每秒的 .43 附近，与上传什么时候结束无关。疑似工具 GUI 每 1 s 刷新一次状态，由这次刷新来判断完成、发下一张 | 推测（日志） |
| R7 | 高亮不消失 | 通用按钮是 `lv_obj_create` 做的；点击时会主动 `lv_group_focus_obj`，而主题给 `LV_STATE_FOCUSED` 配了高亮，所以鼠标点过的按钮会一直亮着 | 代码 |

## 3. 新的运行结构

### 3.1 应用与资源所有权

板端始终运行的**服务**：

- 通信服务：网口收发、EDSC 协议、遥测；
- 输入服务：虚拟输入和板上按键；
- GUI：LVGL、L1 层；
- 性能浮窗。

**媒体应用**同一时刻只能有一个处于活动状态：实时识别、图片识别、图像处理、图形测试（RND 和 LVGL benchmark）、游戏、CoreMark。

| 资源 | 所有者 | 释放时机 |
|---|---|---|
| VIN CH0（摄像头） | 实时识别、图像处理 | 应用 STOPPING 时关闭通道，等 VIN IDLE |
| VIN CH2（内存输入） | 图片识别 | 同上 |
| NPU | 实时识别、图片识别 | 等当前帧的 DONE；不中途打断 |
| PIX、GEO | 图像处理 | 等 IDLE |
| RND | GUI（作为 LVGL 后端）；图形测试运行时归测试 | 测试结束后交还 GUI |
| DISP L0 | 当前媒体应用；没有媒体应用时关闭 | 由 REL_BASE 确认释放 |
| DISP L1 | GUI；游戏运行时缩到浮窗区域 | — |
| ETH TX | 只有通信服务能发；应用通过队列提交 | — |
| ETH RX 窗口 0 / 2 / 3 | 窗口 0：当前大块传输；窗口 2：输入；窗口 3：消息 | 取消大块传输时，复位窗口 0 |
| DDR 缓冲 | 按 `ddr_map.h` 固定分区。每个分区只属于一类应用 | — |

视觉状态 `v` 拆成两部分：三个应用共用的"视觉管线"，以及每个应用各自的会话状态。原来的标志组合改成 3.2 节的状态机。

### 3.2 生命周期

每个媒体应用都实现下面这一组状态，由一个统一的应用管理器驱动：

```
IDLE ──start──▶ STARTING ──资源就绪──▶ RUNNING ──pause──▶ PAUSED
                                         ▲                  │
                                         └──────resume──────┘
RUNNING / PAUSED ──stop──▶ STOPPING ──所有资源 IDLE──▶ IDLE
任意状态 ──可恢复错误──▶ FAILED（页面显示原因；可以"重试"，重试后回到 STARTING）
```

| 操作 | 含义 |
|---|---|
| 暂停画面 | 冻结 L0 和检测框。是否同时停止采集和推理，见第 6 节 Q2 |
| 停止 | 取消正在进行的传输，等引擎空闲，释放资源，回到 IDLE |
| 退出页面 | 先停止，再由管理器返回上一级页面 |
| 切换应用 | 旧应用 STOPPING 完成后，新应用才能 STARTING。不允许两者交叠 |

错误分两类：

- 规格定义的硬件错误（VIN、PIX、GEO、NPU 的错误标志）仍然按 CLAUDE.md §12 处理：打印错误并停机；
- 协议和用户操作错误（长度不符、空间不足、取消）只让当前请求失败，回复错误码，应用保持可用。

### 3.3 调度和预算

- 优先级：通信服务 > 输入服务 > 媒体应用 > GUI。媒体应用每次执行的步骤不超过 2 ms；后处理、伽马表计算、模型加载都切成小片执行。
- GUI 每 16.7 ms 至少得到一次执行机会。输入从网口到达，到 LVGL 读到，最长 16.7 ms（沿用卡 53 的目标）。
- 后处理改为：先对 NPU 输出区做 invalidate，再按 cache 读。目标是解码、排序、NMS 合计 ≤ 35 ms。修完后实测仍然超标时，再考虑把解码搬到 NPU 输出格式上（另行讨论）。

### 3.4 识别耗时的拆分测量

实时识别和图片识别每一帧都记录下面这些时间点（mtime），每秒通过串口输出一行汇总，性能浮窗显示其中的关键几项：

1. VIN 帧完成；
2. NPU 启动；
3. NPU DONE 中断；
4. 应用发现 DONE，即开始后处理；
5. 解码结束；
6. 排序结束；
7. NMS 结束；
8. 检测框交给 GUI；
9. GUI 完成这一帧的刷新。

同时记录每个任务的 CPU 忙时比例，以及 DDR 端口带宽。卡 54 在同一个模型、同一张输入图、同一个门槛下，对比 demo_npu 和 showcase 的这些数据，确认帧率的差距分别来自哪一段。

### 3.5 PC 工具与板端的协议

基本原则：**模式以板端为准**，工具只显示板端回报的状态。

1. **连接**：工具在窗口 3 发连接请求，板端通过网口回复 `HELLO`（EDSC 新类型），内容是程序版本、当前应用和会话状态。工具收到 `HELLO` 才算 PEER 建立，不再依赖串口文字。连接断开或超时，工具界面要明确显示，虚拟设备随之失效。不回退到串口（第 6 节 Q1）。
2. **命令应答**：每个命令都带 `seq`，板端回复三种消息：
   - `ACCEPTED`：已收到；
   - `DONE`：执行完成，或者 `CANCELLED`（取消完成）；
   - `ERROR`：带原因码。

   工具在收到 `DONE` 或 `ERROR` 之前，不发同类的下一个命令。
3. **状态广播**：板端在状态变化时，以及每 1 s，发一次 `STATE`，内容是：当前应用、会话状态、图像处理的全部参数、检测门槛和类别。工具的界面完全按 `STATE` 刷新。
4. **图片识别改为手动逐张**：
   - 工具选择文件夹后建立图片列表，用"上一张 / 下一张"逐张发送；
   - 每张图带一个请求号；板端回传的检测结果也带同一个请求号，工具只接受与当前请求号一致的结果；
   - 工具显示文件名、序号/总数、发送中 / 识别中 / 完成 / 失败；
   - 取消自动批量。
5. **完成判定靠事件，不靠定时刷新**：工具在收到网口消息时立即处理完成事件，不等 GUI 的 1 s 刷新（R6）。

### 3.6 图像处理

- 每项功能都有独立的启用开关，参数放在开关下面：
  - 亮度/对比度
  - 伽马
  - 第一级滤波 S1
  - 第二级滤波 S2
  - 灰度
  - 二值化（阈值）
  - 反色
  - 旋转
  - 缩放
  - 平移
  - 镜像
- 执行顺序按硬件固定：PIX 按 pix-spec 1 的流水线顺序（点运算 1 → S1 → S2 → 点运算 2），然后是 GEO。界面按这个顺序排列，并且画出流向。
- 关闭一项只是把这一级旁路掉，不影响其他项。关闭时参数是否保留，见第 6 节 Q3。
- 板端页面和工具都按 `STATE` 显示同一组参数。任何一边改动，另一边在下一次 `STATE` 时同步。

### 3.7 输入

- **单一所有者**：同一时刻，输入只交给 GUI，或者只交给当前媒体应用（游戏、benchmark）。
- **所有权切换时屏蔽按住的键**：切换时还按着的键和鼠标键先屏蔽，等它们松开以后，新的所有者才能收到。这样一次按键不会被两边各处理一次，R4 就修好了。网口断开或切换页面时，补发所有键和鼠标键的释放。
- **Esc 逐级返回**，每次只退一级：设置弹层 → 页面内的子模式 → 页面 → 上一级列表 → 首页。游戏退出后回到游戏列表，焦点停在原来那个游戏上。
- **只传状态，不传增量**：网口发的是完整状态快照，板端只用最新的一帧，不积压。鼠标位置用绝对坐标，滚轮用累计值。

### 3.8 LVGL 控件与外观

- 控件按语义使用：
  - 按钮用 `lv_button`；
  - 开关用 `lv_switch`；
  - 参数用 `lv_slider`，旁边显示数值；
  - 选择用 `lv_dropdown`；
  - 类别用 `lv_checkbox`。
- 五种状态的样式要分开：悬停（只对鼠标）、键盘焦点（只用 `LV_STATE_FOCUS_KEY`）、按下、选中、禁用。用鼠标点过的控件不留焦点框。
- 页面外观重新设计：由 Codex 在 PC 模拟器上出效果图，用户选定后再实现。效果图放在 `outputs/`，不进仓库。
