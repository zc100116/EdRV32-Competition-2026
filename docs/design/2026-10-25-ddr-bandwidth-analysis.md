## 1. DDR 硬件参数

| 项 | 值 | 来源 |
|---|---|---|
| 颗粒 | 2 × 4 Gbit DDR3（XCCC256M16，兼容 MT41K256M16），x16 × 2 = **32 位**，总容量 **1 GB** | 硬件手册 |
| 速率 | IP 配置为 **1000 MT/s**（颗粒最高 1066） | idf：`DESIRED_DDR3_RATE=1000` |
| 理论带宽 | 1000 MT/s × 4 B = **4.0 GB/s** | — |
| 用户接口 | 256 位，**core_clk = 125 MHz**，256 b × 125 MHz = 4.0 GB/s，与理论带宽正好相等 | idf：`DFI_CLK_PERIOD=8000` |
| 每次突发长度 | `axi_awlen/arlen` 只有 4 位，所以 **≤ 16 拍 × 32 B = 512 B** | IP 端口模板 |
| 地址 | `axi_*addr[27:0]` | IP 端口模板 |
| 行和 bank | 行地址 15 位，列地址 10 位，8 个 bank。一行跨两颗芯片共 **4 KB** | idf |
| 刷新 | tREFI = 7.8 µs，tRFC = 300 ns，**刷新开销约 3.9%** | idf：`DDRC_TREFI=3900`、`DDRC_TRFC=150`（单位为 2 ns 的 DDR 时钟） |
| 换行代价 | tRP + tRCD = 13.5 + 13.5 = **27 ns** | idf |
| 读写换向 | tWTR = 7.5 ns，再加上 CL/CWL 引起的总线空转，**估计每次换向 20–30 ns** [估算] | idf |
| 自动预充电 | `axi_awuser_ap` / `axi_aruser_ap`：每个请求可以单独选择访问后是否关闭当前行 | IP 端口模板 |
| **读数据不能反压** | IP 的读通道**没有 RREADY**，读数据一旦返回就必须收下 | IP 端口模板 |
| 写完成 | 没有标准 B 通道，只有 `axi_wusero_last` / `wusero_id` 表示写数据被取走 | IP 端口模板 |

**最后两条对架构影响很大**：
1. **读不能反压**：适配器发出读命令前，必须先在读返回缓冲里预留一整个突发（512 B）的空间。也就是说，**能同时在途的读请求数，由读返回缓冲的大小决定**。这是 mem_xbar 在途 credit 的物理来源。
2. **写响应由适配器合成**：适配器根据 `wusero_last` 生成 AXI 的 B 响应。spec 要写明：B 响应只表示"数据已交给 DDR 控制器"。在单从设备、控制器内部按序执行的前提下，这足以作为写栅栏使用。适配器设计时需要确认控制器内部的读写顺序 [待 IP 文档确认]。

## 2. 有效带宽 B_eff 估算

以一次 16 拍突发（512 B）为单位，在 DDR 总线上占用 512 B ÷ 4 B ÷ 2（双沿）= 64 个 DDR 时钟，即 **128 ns**。

| 访问模式 | 每个突发的额外开销 | 效率估算 |
|---|---|---:|
| 单路顺序读，同一行连续访问 | 只有刷新 | 约 90–95% |
| 多路顺序流交替，各流落在不同 bank | 控制器可以重叠激活，少量换行 | 约 80–90% |
| 读写混合，每 4 个同方向突发换向一次 | 换向约 25 ns / 512 ns | 约 5% 损失 |
| 读写混合，每个突发都换向 | 换向约 25 ns / 128 ns | 约 20% 损失 |
| 短突发（1–2 拍） | 命令开销占主导 | < 30% |
| 同 bank 不同行冲突 | 27 ns / 128 ns | 约 20% 损失 |

- **规划用值**：B_eff 按 **2.6 GB/s**（约 65%，保守）规划，乐观值约 3.2 GB/s（80%）。Pango 软核控制器的实际调度能力未知，**必须上板实测** [实测]。
- **准入上限**沿用旧框架：0.75 × B_eff ≈ **1.95 GB/s**。各场景的持续流量总和不能超过这个值。

### 2.1 提高 DDR 效率的硬性规则（写进 spec）

1. **能用长突发就用长突发**：所有 DMA 的突发对齐到 512 B，一律用 16 拍。只有行首和行尾允许短突发，必须用字节写使能处理。
2. **读写分组**：仲裁器连续服务同方向的请求，最多 N 个突发（初值 4）再换向。只有 urgent 请求能打断。
3. **帧缓冲按 4 KB 行对齐**：Surface 基址按 4 KB 对齐。同时活跃的 Surface 由分配器错开，落在不同 bank。
4. **自动预充电策略**：顺序流不预充电，保持行打开；一次性随机访问（CPU 缺失、描述符读取）预充电。具体策略在适配器中实现，经过实测后定。
5. **禁止 DDR 里的整帧复制**：Surface 之间只交换所有权，不复制数据（沿用旧框架）。

### 3.3 YOLO 推理流量估算 [估算，NPU 阶段需精算]

YOLOv8n 在 640×384 下：
- **计算量**约 2.61 GMAC（按 640×640 下 8.7 GFLOPs 等比例缩放）。旧设计的 512 MAC 阵列在 150 MHz 下，100% 利用率时需要 34 ms，按 40–60% 利用率算是 57–85 ms，**约 12–17 fps，主要受算力限制**。
- **每次推理的 DDR 流量 B_infer**，按 C16 补齐布局逐层累加：
  - 输入：3.93 MB（C3 补到 C16，浪费了 4 倍以上的空间和带宽。NPU 阶段可以考虑 C4 打包）
  - 特征图写入：约 9.9 MB
  - 特征图读出：旧设计每个 32 输出通道块都要重读一次整层输入，读放大约 2–3 倍，约 20–30 MB
  - 权重：约 3.3 MB
  - **合计约 37–47 MB/次**，再加 20% 余量取 **约 50–60 MB/次**
- 按 15 fps 计约 **0.75–0.9 GB/s**，按 10 fps 计约 0.5–0.6 GB/s。
- 旧文档"假设 0.5 GB/次"高估了 10 倍左右。真实值要在 NPU 阶段用逐层 DMA 计数精确算出。

## 4. 按演示场景汇总

所有场景都包含"显示扫描 + 图层合成"这个底座。两种合成方式在 30 fps、RGB565 输出的条件下流量基本相同：

| 合成方式 | 流量 |
|---|---:|
| A：扫描时叠加（两层实时读） | 111 + 221 = **332 MB/s**，全部是硬实时 |
| B：离线合成（30 fps）+ 单层扫描 | 221（软实时）+ 111（硬实时）= **332 MB/s** |

**两种方式的带宽相同，区别在于硬实时流量的多少、延迟和逻辑复杂度**，这部分留到模块阶段讨论（D4）。下表按 332 MB/s 计。

| 场景 | 组成 | 持续带宽 | 占准入上限（1.95 GB/s）的比例 |
|---|---|---:|---:|
| S1 YOLO 识别 | 底座 332 + 摄像头 55 + NPU 输入 59 + NPU 推理 750–900 + UI 绘制 20 + CPU 50 | **1.27–1.42 GB/s** | 65–73% |
| S2 图像处理 | 底座 332 + 摄像头 55 + GEO 121 + UI 20 + CPU 50 | **0.58 GB/s** | 30% |
| S3 渲染 / LVGL | 底座 332 + 绘制最坏 166 + CPU 50 | **0.55 GB/s** | 28% |
| 压力测试：全部同时开 + 双摄像头 + ETH | 上面全部相加 | 约 1.9–2.1 GB/s | 约 100%（只用于验证，不是演示场景） |

**摄像头 60 fps 时的校核**：摄像头写 ×2、GEO ×2。S2 约 0.75 GB/s（38%），S1 约 1.33–1.48 GB/s（68–76%），都在上限以内。

**NPU 的带宽天花板**：S1 扣除其他流量后，留给 NPU 的上限约 1.95 − 0.55 ≈ **1.4 GB/s**。按每次推理 55 MB 算，DDR 允许的上限约 **25 fps**。要再提高帧率，NPU 阶段必须降低每次推理的流量（输入 C4 打包、提高特征图和权重的片上复用），或者靠实测把 B_eff 提上去。

**结论**：
- S2、S3 余量很大。
- S1 的瓶颈是 NPU。NPU 主要受算力限制，DDR 能满足约 15 fps 的推理。
- 三个场景都能"流畅不卡顿"，前提是硬实时流量（显示扫描、摄像头写入）在任何负载下都能按时得到服务，见第 5 节。

## 5. 实时性分析：除了带宽，还要看最坏等待时间

平均带宽够用，不代表画面不卡。卡顿来自**硬实时 FIFO 在最坏等待时间内被读空或写满**。

### 5.1 时间余量

| 流 | 一行的时间 | 每行数据量 | FIFO 建议容量 | 能容忍的最长等待 |
|---|---|---|---|---|
| 显示扫描（单层） | 22.2 µs（行周期），有效段 17.2 µs | 2560 B = 5 个突发 | 2 行 = 5 KB | 约 22 µs |
| 显示扫描（双层） | 同上 | 7680 B = 15 个突发 | 2 行 = 15 KB | 约 22 µs |
| 摄像头写入 | 约 44 µs（720p30） | 2560 B | 2 行 | 约 44 µs |

### 5.2 最坏等待估算

假设硬实时请求刚好错过一次仲裁，要等的时间包括：
- 当前正在执行的突发：约 160 ns
- 控制器里已经排队的其他请求：在途上限 × 160 ns。所有端口合计在途上限 8 个时约 1.3 µs
- 一次刷新：300 ns
- 一次读写换向：约 30 ns

**合计约 2 µs**，比 22 µs 的容忍度小一个数量级。

结论：**只要所有端口的在途数和连续授权数都有上限，硬实时流就有约 10 倍余量**。urgent 机制只是保险，不应在正常情况下频繁触发。

### 5.3 关键规则

1. **控制器入口的总在途数有上限**（初值 8）。不允许任何一个主设备把 DDR 控制器的队列塞满。旧文档也指出过："只在仲裁器里提高优先级，而 DDR 队列已经塞满 NPU 请求，仍然会错过截止时间。"
2. **NPU 的在途和连续授权都有上限**（初值：读在途 4、写在途 2、连续授权 4 个突发）。
3. 显示扫描在 FIFO 低于 1 行时触发 urgent，摄像头在 FIFO 超过 1 行时触发 urgent。urgent 的触发次数要计数，作为验收指标（正常负载下应接近 0）。

## 6. 端口划分方案

### 6.1 划分原则

- **按实时等级和流量所有者划分**。QoS 等级不同的流量放在不同端口；同一子系统内、等级相同的流量合并，由子系统内部仲裁。
- **PIX 内联在视频输入路径上**，不占 DDR 端口。NPU 输入适配器也是从摄像头流分出来的，写入归入视频输入端口，作为可丢帧的低优先级通道。

### 6.2 已确认：7 个主设备端口

| 端口 | 主设备 | 等级 | 方向 | 持续带宽 | 在途上限（初值） | 其他控制 |
|---|---|---|---|---:|---|---|
| P0 | DISP 显示扫描（含叠加层读取，如果采用方式 A） | **RT** 硬实时 | 读 | 111–332 MB/s | 读 4 | FIFO 低水位 → urgent |
| P1 | VIN 视频输入：cam0 写、cam1 写、NPU 输入写（内部仲裁，摄像头优先，NPU 输入可丢帧） | **RT** 硬实时 | 写 | 55–170 MB/s | 写 4 | FIFO 高水位 → urgent |
| P2 | CPU 网关 | **LAT** 低延迟 | 读写 | ≤ 50 MB/s | 读 1 / 写 1 | 限速：最多占 10% 带宽 |
| P3 | NPU | **BE** 尽力而为，保底份额 | 读写 | 0.5–0.9 GB/s | 读 4 / 写 2 | 连续授权 ≤ 4 个突发；保底份额 30% |
| P4 | RND 渲染器（绘制 + 离线合成，如果采用方式 B） | **SRT** 软实时 | 读写 | ≤ 390 MB/s | 读 2 / 写 2 | |
| P5 | GEO 几何变换 | **SRT** 软实时 | 读写 | ≤ 121 MB/s | 读 2 / 写 2 | |
| P6 | ETH + 性能监视器 | **BE-low** 尽力而为，限速 | 读写 | ≤ 120 MB/s | 读 2 / 写 2 | 限速：最多占 5% 带宽 |

### 6.3 仲裁规则

按突发粒度做调度决策，优先级从高到低：

1. **urgent**：P0/P1 的水位触发。每次 urgent 最多持续 M 个突发（初值 8）。
2. **LAT**：P2 有请求时，在下一个突发边界优先服务，但受限速令牌约束。
3. **饿死保护**：任何端口等待超过阈值（初值 2 µs）就提升优先级。
4. **加权轮询**：在剩下的端口间按权重分配，初值 RT : SRT : BE = 4 : 2 : 3。NPU 的保底份额由权重和饿死保护共同保证。
5. **读写分组**：在不违反 1–3 的前提下，连续服务同方向请求，最多 4 个突发后换向。
6. **全局在途上限**：控制器入口总在途不超过 8，读返回缓冲按 credit 管理（第 1 节"读不能反压"）。

所有初值都由 MEM_XBAR 寄存器配置，硬件复位值即 spec 规定的初值。

### 6.4 可观测性（验收依据）

每个端口计数：请求数、传输拍数、最长等待时间、平均等待时间、urgent 触发次数；全局计数：读写换向次数、DDR 繁忙周期。

## 7. 验证与实测计划

| 项 | 方式 | 执行方 |
|---|---|---|
| B_eff 实测：单路顺序读、单路顺序写、读写混合（1:1，每 4 个突发换向）、多流交替 | 上板，用 DDR 性能监视器或厂商 `ddr3_test` 例程 | Windows 任务卡 |
| 控制器读写顺序、自动预充电的效果 | 上板对照实验 | Windows 任务卡 |
| 场景流量回放：按 S1/S2/S3 和压力测试配置各端口流量发生器，统计各端口最长等待、FIFO 最低水位、urgent 次数 | RTL 仿真，用 DDR 时序模型 | Linux 仿真 |
| 系统级混合负载 | 上板 | P7 系统集成阶段 |

B_eff 实测出来后，回头修正第 2 节的规划值和第 4 节的百分比。如果 S1 的余量不足，先降低 NPU 的帧率目标，而不是牺牲实时流。
