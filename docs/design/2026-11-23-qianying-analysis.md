# 「千影」作品视频分析（易灵思赛题二）

| 项 | 内容 |
|---|---|
| 日期 | 2026-11-23 |
| 来源 | 用户提供的答辩视频（约 3 分钟，1280×720），不入库 |
| 说明 | 下文数字都取自视频里的幻灯片和画面字幕。他们自己标为“团队板测反馈”或“历史解析模型”的数字，照原样转述，标注口径 |

## 1. 他们做了什么

| 项 | 内容 |
|---|---|
| 平台 | 易灵思 Ti60F225，Sapphire RISC-V 软核（RV32I + CFU 自定义指令），系统时钟 100 MHz 提到 200 MHz（setup 余量 +0.107 ns，hold 余量 +0.026 ns，分析 Fmax 约 204.4 MHz） |
| 显示 | HDMI **640×480@60**，帧缓存在 DDR3，RGB565；三缓冲，VSYNC 时锁存翻页 |
| 渲染引擎 | BitBlt 2D 引擎：填充、拷贝、颜色键、Alpha 混合、硬件文本、**同素材多目标批处理** |
| 主要指标 | T ≤ 2300（2044 个怪物槽 + 256 个敌弹池）时 60 FPS，口径为“团队板测反馈”；T 是目标数，实际绘制量为 M+B |
| 资源 | LUT4 24,261，FF 18,368，RAM10 160，DSP 13（他们的 V89 实现报告） |
| 演示 | 弹幕生存游戏（主演示，屏幕上方实时显示怪物数、敌弹数、目标负载、渲染帧率、实际帧率）；颜色键 + Alpha 演示；软硬件同屏对比；《元素荒原》2.5D 斜视角开放世界 |

## 2. 关键技术

| 技术 | 做法 | 解决什么问题 |
|---|---|---|
| 同素材多目标批处理 | 一次 START 画同一张素材的一长串目标位置，内部按 48 项分块装载 | 去掉“一个精灵一条命令”的开销。2000 个怪物只用了几种素材，命令数从几千条降到几条 |
| 8 KB 源缓存 | 同一素材读一次，画到所有目标位置 | 素材不必从 DDR 重复读 |
| 颜色键优先 | 命中透明色就保留背景，否则走 Alpha 混合或直通；写回时用 WSTRB 字节使能 | 只有颜色键、没有半透明的精灵，可以不读目标像素，直接按字节使能写 |
| 定点 Alpha | Cout = Cb + ((Cf − Cb)·A + 128) >> 8；一个 32 位字里的两个 RGB565 像素并行算；A = 255 时跳过乘法 | 每拍 2 个像素 |
| 四级访存优化 | 128 位突发聚合（按 4 KB 边界拆分）、8-bank 写缓冲、读路径预取、弹性写流水 | 提高 DDR 效率。他们的历史模型给出拷贝 1.56 倍、颜色键 1.67 倍的周期收益（标注“不等同整机实测 FPS 加速比”） |
| CFU 轮询 | 用自定义指令查询引擎状态，约 2 拍返回，替代 APB 读 | 减小 CPU 等待引擎的开销 |
| 软件减负 | V85 相对 V84，逻辑段耗时 4545 µs 降到 2426 µs（−46.6%） | 游戏逻辑本身也是瓶颈 |

**版本演进**（他们的表格）：

| 版本 | 时钟 | 负载 | 帧率 |
|---|---|---|---|
| V26 | — | 320 个精灵 | 60 |
| V48 | 150 MHz | 约 1600 个怪物 | 59 |
| V84 | 200 MHz | 1886 | 55 |
| V86 | 200 MHz | 2087 | 57 |
| V89 | 200 MHz | T ≤ 2300 | 60（板测反馈） |

## 3. 判断

1. **架构上并不特殊**：仍然是“DDR 帧缓存 + BitBlt 引擎”，和我们的 RND 属于同一类。他们能跑 2000 多个精灵，靠的是下面四点，而不是新算法：
   - 分辨率低：640×480 RGB565，约 31 万像素，只有我们 1280×720 的 1/3；
   - 批处理命令：同一素材画多个目标，命令开销降了几个数量级；
   - 颜色键用字节使能写回，不读目标像素；
   - 游戏代码直接发命令，不经过 LVGL 这样的通用界面库。
2. **绘制量估算**（假设精灵为 16×16，视频中没有给出精灵尺寸）：
   - 每帧 2300 × 256 ≈ 59 万像素，60 帧约 35 M 像素/秒；
   - 写带宽约 70 MB/s，加上显示扫描 640 × 480 × 2 B × 60 ≈ 37 MB/s；
   - 这对 DDR3 来说很小，说明瓶颈在命令开销和访存效率，不在原始带宽。
3. **“3D 像素游戏”其实是 2.5D**：《元素荒原》是斜视角（等距投影）的二维贴图，按深度排序后从后往前画（他们的字幕原话是“通过二维坐标投影和深度排序实现”）。它没有三角形光栅化，也没有深度缓存。素材用 RLE 压缩，从 45.5 MB 压到 5.6 MB。
4. **资源很少**：约 2.4 万 LUT4。我们的 PG2L200H 约有 16 万 LUT，加上 415 个 DRM，可以用片上 RAM 换掉 DDR 读改写。

## 4. 对我们学习项目的启示

| 方向 | 做法 | 与千影相比 |
|---|---|---|
| 照着做 | DDR 帧缓存 + 批处理 BitBlt。可以复用 RND 的像素流水和访存部分，补上批处理和字节使能写 | 能达到同一个量级；学到的新东西不多 |
| **超过它（推荐）** | 低分辨率片上合成 + 硬件精灵表 + 图块地图，CPU 只改表；再加一个真正的 3D 光栅化单元（三角形、纹理、片上深度缓存） | 估算 60 fps 下约 9,000 个 16×16 精灵（每拍 1 个像素），每拍 2 个像素约 18,000 个，比 2300 高一个量级；而且是真 3D，不是 2.5D |

演示游戏要原创，不照搬他们的弹幕生存或《元素荒原》的设计和素材。
