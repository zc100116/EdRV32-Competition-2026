# 决赛演示：人体关键点手势操控自研游戏

## 1. 背景和问题

- 决赛演示需要一个完整的应用场景，而不是逐项介绍功能。场景既要融合芯片的主要功能，又要有好的现场效果。
- 可编程视觉流水线已放弃：部分组合卡顿，见 `2026-11-14-showcase-vision-pipeline.md` 第 8 节。
- 用户 2026-11-14 要求：场景不需要额外道具。

## 2. 约束

- 实时识别的 CPU 预算（`docs/reports/2026-11-14-perf-sched-isr-board.md`）：
  - CPU 做后处理时，CPU 空闲只剩 8%，帧率 21–23 fps；
  - 硬件后处理（卡 75 的比特流）可以把每帧约 20 ms 的 CPU 解码降到约 1 ms（估算）。
- NES 单独运行就占 89–97% 的 CPU（卡 68 R2 上板，`showcase_nes.log`），设计上是独占场景。
- 摄像头到识别结果的端到端延迟约 110–120 ms（CPU 后处理）。
- NPU 规格 2.1 的算子覆盖 YOLOv8n-pose。硬件后处理固定 80 类：pose 模型把类别输出补到 80 通道，通道 1–79 恒为 −128，不改 RTL。

## 3. 可选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 路口边缘智能盒 | 用到的功能最全 | 需要平板、地贴、灯光等道具 |
| 无人值守展台哨兵 | 无道具，识别人和随身物品 | 交互性一般 |
| **手势操控游戏** | 无道具；评委直接上手；识别和渲染同屏展示 | 依赖关键点模型精度和 CPU 余量 |

## 4. 决策（用户 2026-11-14）

采用人体关键点识别手势、操控游戏的方案，按以下顺序推进：
1. **离线评估 YOLOv8n-pose**：编译、INT8 量化、参考模型精度和 NPU 耗时估算（T-POSE-EVAL）；
2. **单独上板关键点检测**：骨架显示和每帧耗时；
3. **接入自研游戏**：画面和交互方式另行详细设计。

协调者的建议，供第 3 步设计时参考，尚未确认：
- **主角用自研游戏，不用 NES。** 原因：
  - CPU 余量：NES 本身已占满 CPU；
  - 延迟：NES 游戏按帧精确的按键设计，不适合约 100 ms 延迟的体感输入；
  - 自研游戏由绘制引擎渲染，更能体现硬件；
  - 公开比赛不宜展示商业 ROM。
- NES 只作为"姿态手柄"彩蛋，前提是卡 75 布通、CPU 有余量，且使用自制或免费 ROM。
- **手势只用上半身关键点**（鼻、肩、肘、腕），用规则判断，加防抖和滞回。以身体位置的连续控制为主，支持双人。
- **画面布局**：主画面为游戏，角落是带骨架的摄像头小窗，另一角显示性能（NPU fps、端到端延迟、CPU 和绘制引擎占用）。

## 5. 影响

- `tools/npu`：增加 pose 编译方案和评估脚本（T-POSE-EVAL）。
- 第 2、3 步：
  - 板端增加关键点解码、手势判断和自研游戏；
  - 模型可以和检测模型并存于 DDR，按场景切换；
  - 规格（NPU 后处理、OUTPUT 布局）是否需要修订，在评估后确定。
- 不改 RTL。

## 6. 状态

已决定方向（2026-11-14）。游戏的画面和交互方式，在第 1 步评估结果出来后另行设计。
