## 1. 背景和问题

SoC 规格 8.8 和第 10 节把 RND/DISP 的图层合成方式、图层数和格式、命令格式留给模块阶段；图像通路记录把 Q3（合成方式）、Q4（S2 显示形式）推迟到 RND 阶段。

用户对渲染器的要求（2026-10-29）：
1. CPU 能顺畅跑 LVGL：CPU 只分发绘制任务，渲染器快速画出来。
2. 能跑经典小游戏（类超级玛丽），支持精灵。
3. 图层融合。

要决定的问题：

| 编号 | 问题 | 结论 |
|---|---|---|
| Q1 | 图层合成方式和层数 | A 两层扫描叠加（用户 2026-10-29） |
| Q2 | RND 命令集范围 | T2（用户 2026-10-29） |
| Q3 | 游戏路线 | G3：自制游戏为主线，NES 纯软件移植实测；实测效果不好再考虑加硬件（用户 2026-10-29） |
| Q4 | 资源预算 | VIN + PIX + DISP 12K、RND 10K 作为开发初值，标 [待定]，按 B3 实测定稿（用户 2026-10-29） |

## 2. 约束

- RND：mem_xbar P4（软实时，读写），媒体 APB 槽 4，PLIC 源 11，clk_mem 125 MHz，复位 `rst_mem_n`；公共寄存器布局和命令式工作模式（SoC 7.1、7.2：DESC_BASE/COUNT/DOORBELL，完成后置 DONE）。
- DISP：P0 读口带 `urgent_o`，扫描 FIFO 跨到 clk_pix（X5、X6）；输出 1280×720@60。
- DDR 访问都经过 `dma2d_rd`/`dma2d_wr`（SoC 8.11），引擎内多客户端先在引擎内仲裁。
- 资源（SoC 9.3）：RND ≤ 12K LUT；VIN + PIX + DISP ≤ 10K LUT，media r4 实测已经 9888 LUT（`docs/reports/2026-10-29-timing-media-top-r4.md`）。
- 带宽（SoC 9.1）：S1 ≤ 1.5 GB/s，S3 ≤ 0.6 GB/s，总上限 0.75 × B_eff = 1.95 GB/s（B_eff 规划值 2.6 GB/s，待实测）。
- RND 只能访问 DDR：CPU 的 SRAM、ROM 中的数据（字体、图片）对 RND 不可见。
- LVGL v9 的绘制模型：所有绘制拆成绘制任务，绘制单元用 `evaluate_cb` 打分认领、在 `dispatch_cb` 中执行，没被认领的任务由 CPU 软件绘制单元完成。所以硬件只需覆盖高频、像素量大的任务，其余由 CPU 完成也能正确显示。

## 3. Q1 图层合成方式

### 3.1 可选方案

共同前提：一帧 RGB565 为 1.84 MB，一帧 ARGB8888 为 3.69 MB；60 Hz 扫描。

| | A 两层扫描叠加 | A 三层扫描叠加 | B 离线合成（旧工程） |
|---|---|---|---|
| 做法 | DISP 同时读底图层（RGB565）和 UI 层（ARGB8888），逐像素混合后输出 | 底图层 + 中间层 + UI 层 | RND 读底图和前景，合成一张完整 RGB565 帧写回 DDR，DISP 单层扫描 |
| 硬实时读（全屏全开，**估算**） | 110.6 + 221.2 = 332 MB/s | 553 MB/s | 111 MB/s |
| 合成流量（软实时，**估算**） | 0 | 0 | 每次合成读 1.84 + 3.69、写 1.84 MB，30 fps 约 221 MB/s，60 fps 约 442 MB/s |
| 视频和 UI 同步 | 两层各自在 VBlank 翻页，互不等待 | 同 A | 需要帧控制器（旧工程的底图保留、单前景互斥、三目标缓冲轮转、写保护） |
| 显示延迟 | 最低 | 最低 | 多一次合成（全屏约 4 ms 加排队） |
| 硬件卷轴 | 有（底图层开窗偏移） | 有 | 无，滚屏要重画 |
| 硬件增量（**估算**） | DISP +1.5K LUT、+4 DRM | DISP +3K LUT、+8 DRM | RND +3–4K LUT（合成通路、帧控制器） |

带宽估算公式：每层流量 = 1280 × 720 × 每像素字节数 × 60。合成流量 = (1.84 + 3.69 + 1.84) MB × 合成帧率。

### 3.2 决策：A 两层

理由：
- 三个场景、LVGL 和游戏卷轴都能自然实现；
- 软件最简单，画完就翻页；
- 不需要帧控制器；
- 硬件增量最小。

332 MB/s 的扫描流量在架构阶段的带宽规划中已经计入（S3 的"底座 332 MB/s"）。需要第三层时，用 RND 把内容画进 UI 层。

### 3.3 两层的规定（写进 DISP 规格 v0.3）

| 项 | 底图层 L0 | UI 层 L1 |
|---|---|---|
| 格式 | RGB565，不透明 | ARGB8888，**非预乘** alpha（理由见 3.4） |
| Surface | 基址、跨距可设，Surface 可以大于屏幕 | 基址、跨距可设 |
| 窗口 | 屏幕显示 Surface 中从 (`SCROLL_X`, `SCROLL_Y`) 开始的 1280 × 720 区域（硬件卷轴），X 方向 1 像素粒度 | 屏幕上的位置 (`X`, `Y`) 和大小 (`W`, `H`)，只读这个矩形；矩形外 L1 视为全透明 |
| 透明度 | 无 | 全局透明度 `OPA`（0–255），与逐像素 alpha 相乘 |
| 开关 | 各自使能；L0 关闭时底色为黑 | 各自使能 |
| 翻页 | 各自的 NEXT_BASE（以及 L0 的 SCROLL、L1 的位置），在帧边界锁存；各自报告 SWITCH 和释放的旧 Surface | 同左 |

混合公式：
- out = (a·F + (255 − a)·B + 127) / 255
- a = α_pixel × OPA / 255
- F 为 L1 颜色，B 为 L0 颜色（RGB565 先按 DISP 2.3 展开到 8 位）。

舍入的具体写法在 DISP 规格中逐位规定，参考模型与之一致。

实现方向：
- **混合放在 clk_mem 侧**。读控制按行交替读两层（一个 P0 端口，DISP 内两个 `dma2d_rd` 仲裁），混合后写入现有扫描 FIFO（X5）。
- 混合吞吐要求为 74.25 Mpx/s 的平均速率，clk_mem 侧 1 像素/拍（125 Mpx/s）够用。
- 这样**不新增跨时钟域**。
- FIFO 中的像素格式（RGB888，或混合后舍入为 RGB565）在 DISP 规格中定 **[待定]**，初值 RGB888。
- L0 的 X 方向 1 像素卷轴：每行多读一拍、在拍内移位，因为 `dma2d_rd` 的基址要求 32 B 对齐。

**卷轴不做环绕**。一关横版地图可以整张放进 DDR：例如 4096 × 720 RGB565 为 5.9 MB，跨距 8192 B。软件用 TILEMAP 一次画好整关，滚屏只改 `SCROLL_X`。

**实时性**：
- 有效行期间两层同时读：(2560 + 5120) B / 22.2 µs ≈ 346 MB/s。
- 扫描 FIFO 至少 2 行、紧急授权的要求（SoC 8.8）不变，必须在 SoC 级仿真的 S1 满负载下证明不读空。
- **估算**：S1 1.5 GB/s 加 L1 221 MB/s，约 1.72 GB/s，低于 1.95 GB/s。

### 3.4 L1 为什么用非预乘 alpha

- 旧工程前景用预乘。但 LVGL v9 的 ARGB8888 显示缓冲是非预乘的。
- **CPU 软件绘制单元和 RND 写同一块缓冲**：没被 RND 认领的任务由 LVGL 软件画进同一个 L1。
- 两者格式不一致，就要在每次软件绘制后转换。
- 所以 L1 和 RND 的 ARGB8888 目标都用非预乘。RND 内部可以先转成预乘再混合，写回时转回去。

### 3.5 三个场景和游戏的图层用法

| 场景 | L0 | L1 |
|---|---|---|
| S1 目标检测 | 摄像头帧（CH0 环），每帧翻页 | RND 画检测框和标签。检测结果更新时，清除上次画过的矩形再重画 |
| S2 图像处理 | PIX/GEO 结果 | 菜单、参数、帧率（只开需要的矩形） |
| S3 LVGL | LVGL 显示缓冲：RGB565，全屏双缓冲（注） | 关闭，或只用于鼠标光标等小块内容 |
| 游戏 | 整关瓦片地图，硬件卷轴 | 精灵和得分条，双缓冲，每帧重画 |

注：S3 的界面是不透明全屏，放在 L0 用 RGB565。
- 带宽是 ARGB8888 的一半。
- RGB565 是 LVGL 最常用的格式。
- 网口输出可以直接发 L0（3.6）。

**S2 显示形式（图像通路 Q4）**：全屏显示处理结果加 L1 叠加信息。原图与结果对比、画中画等形式由 RND 的 BLIT 缩放画进 L0，是软件层面的选择，不需要硬件支持。

### 3.6 对网口视频输出的影响

B2 设计记录 3.4a 的网口视频发的是"最终显示帧"。扫描叠加后，DDR 中不存在合成好的帧。B3 起的规定：

- 网口发送帧以 L0 Surface 为基础。
- L1 没有内容（S3、游戏以外的纯视频）时，直接发 L0。
- L1 有内容时：
  1. RND 用 COPY 把 L0 复制到 TX 缓冲；
  2. 按软件记录的 L1 脏矩形用 BLIT 叠加（只叠加画过的区域）；
  3. 发送这块缓冲。
- **估算**：COPY 每帧读写 1.84 MB 各一次，30 fps 约 111 MB/s。叠加量取决于检测框面积。
- S1 的检测框也一直在 EDDT 结果里，调试工具可以自己画框，所以 S1 可以只发 L0。
- B2 不受影响：B2 没有 RND 和 L1，CPU 直接在摄像头帧上画框（B2 设计记录 3.4）。

## 4. Q2 命令集

### 4.1 可选方案

| 档 | 内容 | 评价 |
|---|---|---|
| T1 最小 | 填充、贴图、搬运 | 硬件小、开发快；文字、圆角、阴影全由 CPU 完成，LVGL 不顺 |
| T2 | 旧工程命令集补齐（见 4.2） | 覆盖 LVGL 高频任务和游戏，预计在 12K LUT 内（**估算**，待 PDS） |
| T3 全面 | T2 加线、弧、三角光栅化，加 RND 内部双线性变换 | 超出 12K 预算，工作量大；这些任务在 LVGL 中频率低 |

### 4.2 决策：T2

**命令列表**：
- 每条命令固定 64 B、64 B 对齐（沿用旧工程，命令 DMA 一次取 2 拍）。
- 按列表顺序执行，命令之间的先后关系就是绘制顺序。
- 所有命令都有目标矩形和裁剪矩形。
- 全部执行完、最后一个写响应返回后置 DONE（SoC 7.2）。

**目标格式**：RGB565、ARGB8888（非预乘）。

**源格式**：
- RGB565、ARGB8888；
- A1、A2、A4、A8（字形和掩码）；
- I4、I8（带调色板的索引色，用于瓦片、精灵和 NES 画面）。

调色板放在 DDR 中，由命令给出地址。索引格式是否在首版实现 **[待定]**，初值实现 I8。

| 命令 | 内容 | 对应 LVGL 任务 |
|---|---|---|
| FILL | 纯色或水平/竖直线性渐变（CPU 算 Q16 步长）；可带圆角半径，圆角边缘抗锯齿覆盖率；整体透明度 | FILL |
| BORDER | 圆角边框：宽度、四边选择、抗锯齿 | BORDER |
| GLYPH | A1/A2/A4/A8 位图按颜色和透明度着色混合 | LETTER（LABEL 拆成逐字 LETTER） |
| BLIT | 源格式见上：<br>• 整体透明度、重新着色（按比例混入一种颜色）、颜色键；<br>• 最近邻缩放（Q16 步长）、水平/竖直翻转；<br>• 混合模式：正常、相加、相减、相乘 | IMAGE、LAYER |
| COPY | 同格式矩形搬运，同一 Surface 内允许重叠 | 缓冲同步（LVGL 双缓冲的脏区复制）、网口发送帧 |
| BOX_SHADOW | 宏命令：圆角掩码 → 两遍盒式模糊（DDR 临时区）→ 着色混合 | BOX_SHADOW |
| BLUR | 对目标区域做两遍盒式模糊（DDR 临时区） | BLUR |
| TILEMAP | 按瓦片索引表画一块区域：<br>• 瓦片 8×8 或 16×16；<br>• 瓦片格式与 BLIT 源格式相同，带颜色键；<br>• 索引表项含瓦片号和水平/竖直翻转（位宽在 RND 规格中定）；<br>• 起点可以不对齐瓦片 | 游戏背景（不属于 LVGL） |

**不由硬件实现，留给 CPU 软件绘制单元**：
- LINE、ARC、TRIANGLE；
- MASK_RECTANGLE、MASK_BITMAP；
- VECTOR、3D；
- 径向和锥形渐变；
- 任意角度旋转。RGB565 整帧旋转可以用 GEO；带 alpha 的图片旋转由 CPU 完成。

**数据通路**（沿用旧工程的结构）：
- 2 像素/拍的 alpha 流水线，125 MHz 下 250 Mpx/s。FILL（圆角）、BORDER、GLYPH、BLIT、TILEMAP、BOX_SHADOW 着色共用这一条。
- 纯色填充和同格式不透明搬运走 256 位快速通路：每拍 16 个 RGB565 像素或 8 个 ARGB8888 像素。
- 目标区域按行做读改写，读写都通过 `dma2d_rd`/`dma2d_wr`。
- 写回凑满突发再发；跨命令的写合并缓存不做，以实测数据决定。

**旧工程中不再沿用的部分**：
- 合成 DMA 和帧控制器（Q1 选 A）；
- 写保护器（CLAUDE.md 第 12 节：Surface 所有权由软件和 SoC 7.3 协议保证）；
- 旧的系统级互连。

**性能指标**（写进 RND 规格，全部 **[待定]**，B3 以 PDS 和上板实测定稿）：

| 项 | 开发初值 |
|---|---|
| 全屏 ARGB8888 纯色填充 | ≤ 3 ms |
| 全屏 RGB565 纯色填充 | ≤ 1.5 ms |
| alpha 通路持续吞吐（BLIT ARGB8888 → ARGB8888，1:1，大矩形） | ≥ 1.5 像素/拍 |
| LVGL `lv_demo_benchmark` 平均帧率 | 由 B3 实测定稿 |

### 4.3 LVGL 接入

- 软件提供一个 LVGL 绘制单元：
  - `evaluate_cb` 认领 4.2 表中的任务类型；
  - 对超出硬件能力的参数（例如带旋转的 IMAGE、径向渐变）不认领，交给软件单元。
- `dispatch_cb`：
  1. 把任务翻译成命令，写进 DDR 命令列表；
  2. 清理 cache（SoC 7.4）；
  3. 写 DOORBELL；
  4. 等 DONE 中断。
- 一次门铃批量提交几条任务，**[待定]**，以 B3 实测决定。
- CPU 软件单元和 RND 写同一块缓冲。缓冲区域的 cache 维护在两者交替时进行：RND 写完后作废，CPU 写完后写回。具体规则在 RND 驱动的设计中写明。
- 字体、图标、图片必须放在 DDR（RND 看不到 SRAM）：链接脚本为它们单独划一个 DDR 段，属于 B3 软件工作。
- 显示：
  - S3 用 L0 RGB565 全屏双缓冲；
  - `flush_cb` 写 DISP 的 L0 NEXT_BASE，等 SWITCH 后返回。
- LVGL 源码作为 `third_party/lvgl` git 子模块，锁定到 B3 开始时最新的 v9.x 稳定版 tag（用户 2026-10-29）；加入时同步更新 CLAUDE.md 第 2 节的 `third_party/` 说明。

## 5. Q3 游戏路线

### 5.1 可选方案

| 方案 | 内容 | 评价 |
|---|---|---|
| G1 | 只做自制游戏 | 风险最小，但不尝试 NES |
| G2 | NES 模拟器加硬件 PPU 辅助（RND 增加按扫描行取滚动和换页状态的渲染模式） | 工作量和风险最大；NES 依赖逐扫描行变化的滚动（例如超级玛丽顶部固定的状态栏），硬件要按行重建 PPU 状态 |
| G3 | 主线自制横版游戏；NES 模拟器纯软件移植实测 | 主线完全靠 TILEMAP + BLIT + 卷轴，NES 不额外加硬件 |

NES 的估算：
- 我们的 CPU 在 100 MHz 下约 360 CoreMark（B1 实测 O2 3.603 CoreMark/MHz）。**估算**算力约为原版 ESP32 的一半。原版 ESP32 在 240 MHz 下运行 nofrendo 接近全速但有掉帧。
- 由此推测，纯软件约为半速（推测，待实测）。
- PPU 画面渲染约占模拟器时间的一半。

### 5.2 决策：G3，实测效果不好再考虑硬件

**自制游戏**：
- L0 是整关瓦片地图（TILEMAP 画一次，`SCROLL_X` 卷轴）。
- L1 是精灵和得分条，双缓冲，每帧 BLIT 重画。
- 输入用 KEY1–4（GPIO0 位 0–3，SoC 3.5）。
- 游戏逻辑在 CPU。

**NES**：
- 移植一个开源模拟器（纯软件）。
- 模拟器输出 256×240 的 I8 索引帧，由 RND BLIT（I8 + 调色板 + 最近邻放大 3 倍，768×720）画进 L0。这样 PPU 之后的格式转换和放大由 RND 完成，不需要为 NES 专门加硬件。
- 记录实测帧率。

**后续决定**：
- 实测效果不好时，单独写设计记录评估硬件 PPU 辅助（G2），由用户决定是否增加。
- 用户原话为"后续nes实测效果不好加邮件"，按上下文理解为"加硬件"。

**其他约束**：
- 板上没有音频输出，DISP 不发送 HDMI 数据岛，所以没有声音。
- 演示只用自制或公开授权的 ROM，不用商业 ROM。

## 6. Q4 资源预算

- SoC 9.3：VIN + PIX + DISP ≤ 10K LUT，media r4 实测 9888 LUT。DISP 增加第二层后预计 +1.5K LUT（**估算**），放不进这一档。
- RND 预算 12K，T2 的实际规模待 B3 实测。旧工程 render RTL 约 7.8K 行，没有综合数据；T2 去掉了旧工程的合成通路和帧控制器。

| 方案 | 内容 |
|---|---|
| 1 | VIN + PIX + DISP 调到 12K、RND 调到 10K，合计 108K 不变 |
| 2 | VIN + PIX + DISP 调到 12K、RND 保持 12K，合计 110K |
| 3 | 不改预算，DISP 的图层部分计入 RND 的 12K（模块边界与预算边界不一致） |

**决策**：
- 按方案 1 作为开发初值：VIN + PIX + DISP 12K、RND 10K，合计 108K。
