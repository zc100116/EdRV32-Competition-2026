# showcase R4 规划：流畅度、调度、应用重组、界面部件和积木塔

## 1. 背景和问题

卡 91（b3 `3dda798f`，卡 75 比特流）上板后，用户 2026-11-16 的反馈和新要求：

1. **卡 91 反馈**：整体还可以，但有两处问题：
   - 手移动过快时有"断触"感；
   - 脸颊贴纸离鼻子贴纸太近。
2. **卡顿**：画面一卡一卡的。抓取测试中拿着方块移动时最明显。
3. **积木塔**：把抓取测试改成 2D 搭积木游戏。要求：
   - 一块一块往上搭；
   - 方块有不同材质、不同形状；
   - 方块有体积，会互相碰撞、堆叠。
4. **应用重组**：应用已有 15 个，需要重新规划。
5. **界面**：
   - 页面改用 LVGL 的专用部件，不再用最基础的对象拼；
   - 加对齐方面的选项；
   - 部分文字要醒目。
6. **调度**：规划好应用、中断、任务之间的调度，保证整体流畅、不卡顿；另外做一个实时操作系统（RTOS）版本作对照。

## 2. 卡顿的原因

下面每一条都给出了推断依据。标"推断"的，P0 先加测量再确认。

| 编号 | 原因 | 依据 | 影响 |
|---|---|---|---|
| C1 | **同步显示后 CH0 画面槽不够**（推断） | 同步模式下，一个槽从采集一直占到被下一帧替换，约 e2e + 1 个显示周期 + 1 个采集周期，即 104 + 50 + 33 ≈ 190 ms。4 个槽能支撑的帧率约为 4 / 0.19 ≈ 21 fps，与实测 19–20 fps 一致。卡 90 没有同步显示，同一页面是 25 fps | 帧率从 25–27 掉到 19–20 |
| C2 | **结果到上屏太慢** | gui 一项：人脸页 68 ms，体感页 43 ms。CPU idle 仍有 65–89%，说明大部分时间不是在计算，而是在等待：<br>- GUI 定时器到期；<br>- RND 完成（GUI 任务在 `sched_wait_flag` 中 WFI）；<br>- DISP 帧边界：同步提交要在 FRAME 中断里写地址，下一帧才生效，最多多等 33 ms | 延迟增大；同时占槽时间变长，加重 C1 |
| C3 | **画面更新节奏不均** | 显示器固定 60 Hz（disp-spec，时序不可配）。20 fps 的画面每帧应停 3 个刷新周期，实际在 2–4 个之间跳 | 平均帧率相同，看起来也会一顿一顿 |
| C4 | **抓取测试的 30 Hz 定时器和识别结果不同步** | `page_grab.c` 中重力动画用 33 ms 定时器推进，光标和被拿着的方块随识别结果（约 20 fps）更新，两者形成拍频：有的显示帧方块走两步，有的不动；L1 也会在两帧摄像头画面之间单独翻转。<br>状态文字面板（900×94，半透明）每次 tick 都会重绘 | 抓取测试中方块"一卡一卡"的直接原因 |
| C5 | **快速移动时丢手**（推断） | OV5640 自动曝光的上限约为一整帧，即 33 ms（`0x3a02/03`）。室内光线下，快速移动的手会严重拖影，检测不到；丢手后光标停住，再出现时跳一下。拿着的方块可能被直接放下 | 用户说的"断触" |
| C6 | **协作式调度下，GUI 的一步不可打断** | GUI 一步（LVGL 定时器处理加渲染）可以长达几十毫秒。期间应用任务（视觉服务的发布、游戏逻辑）无法运行，即使 CPU 只是在 WFI 等 RND。<br>NPU 下一帧已经由中断直接启动（ISR 重启，卡 77），但结果的发布和游戏状态的推进仍然排在 GUI 后面 | 延迟和抖动都被放大 |

## 3. 调度规划

### 3.1 现状

| 层级 | 内容 |
|---|---|
| 中断（PLIC） | VIN、NPU、PIX、GEO、RND、DISP、ETH、UART0、GPIO0；CLINT 只用于性能采样。<br>NPU 完成中断中直接启动下一帧推理。<br>DISP FRAME 中断中同步写 L0 和 L1 的地址 |
| 协作任务<br>（数字小者优先） | 0 通信服务：UART、ETH、按键；<br>1 当前应用：视觉服务、会话、当前应用的 step；<br>2 图形界面：LVGL 定时器和渲染 |
| 游戏逻辑 | 写在 LVGL 定时器里（16 ms、33 ms），与渲染在同一步中执行 |

### 3.2 目标

| 指标 | 目标（交互页面） |
|---|---|
| 识别帧率 | 同步页不低于非同步页（≥ 25 fps，手势模型的上限约 26 fps） |
| 结果到上屏（gui） | 中位数 ≤ 25 ms |
| 上屏间隔 | 稳定，相邻两帧之差 ≤ 1 个刷新周期（16.7 ms） |
| 游戏物理 | 固定步长 60 Hz，与渲染无关 |
| 任何任务的单步最长时间 | ≤ 10 ms；渲染除外，渲染按页面预算 |

### 3.3 方案（主线：协作式，改结构）

1. **中断只做登记和启动**：每个中断处理时间 ≤ 50 µs。
   - VIN：槽位登记；
   - NPU：启动下一帧（已有）；
   - DISP：切换地址；
   - RND：标记完成。
   - 测量每个中断的次数和累计时间。
2. **游戏逻辑移出 LVGL 定时器**：
   - 物理和规则在应用任务中，按固定 60 Hz 步长推进；
   - GUI 只读取状态快照来绘制（模型与视图分开）。
   - 这样可以消除 C4 的拍频，渲染慢也不会拖慢物理。
3. **同步页按结果驱动绘制**：
   - 一个识别结果对应一次绘制、一次上屏；
   - 两个结果之间不单独翻转 L1；
   - 上屏间隔用 DISP 帧计数稳定下来（3.5 节的 D1）。
4. **GUI 等待 RND 时让出 CPU**：
   - `sched_wait_flag` 等待期间，允许运行已就绪的、不访问 LVGL 的任务（视觉服务、游戏物理）；
   - 访问 LVGL 的代码只在 GUI 任务中运行。
5. **槽位**：CH0 由 4 个增加到 6 个。
   - DDR 中 `0x0600_0000` 起每槽 2 MB，到 `0x0700_0000` 之间可放 8 个，不需要调整其他区域；
   - 改动写进 b2 软件设计 3.3 的表格。
6. **每页绘制预算**：
   - 动态区域不用阴影、模糊、整层半透明；
   - 静态面板只画一次；
   - 每页实测绘制时间，超出预算的页面单独优化。
7. **测量（P0 先做）**，每秒一行 `sched`：
   - 各任务的占用和最长单步；
   - 各中断的次数和时间；
   - VIN 丢帧数；
   - 上屏间隔的直方图（2/3/4/≥5 个刷新周期各多少次）；
   - gui 分段：等定时器、渲染（RND / 软件）、等帧边界。

### 3.4 RTOS 对照版本

- **起点**：已有的 FreeRTOS 版本（分支 `zc100116/task-vis-rtos` `7a54602b`）。它基于较早的 `ea11656c`，没有上过板（卡 71 未执行）。
- **移植**：移植到最新代码。与协作版共用同一份应用代码，构建时用 `SHOWCASE_SCHED=coop|rtos` 选择。这个参数用于评估，有结论后删除较差的一种。
- **任务划分**：

  | 优先级 | 任务 | 内容 |
  |---|---|---|
  | 最高 | 视觉 | 发布结果、管理槽位 |
  | 高 | 游戏物理 | 60 Hz，`vTaskDelayUntil` |
  | 中 | GUI | 唯一调用 LVGL 的任务 |
  | 低 | 通信 | UART、ETH 调试工具 |
  | 空闲 | — | WFI |

  - CoreMark 和 NES 独占运行时，暂停系统时钟节拍。
- **对照方法**：同一块板、同一个比特流、同样的页面和动作，A/B 两个 ELF。比较以下指标：
  - fps、e2e、gui；
  - 上屏间隔直方图、物理步长抖动；
  - 上下文切换次数、内核占用；
  - CoreMark 分数、LVGL benchmark 帧率。

### 3.5 待定

D1：交互页面的画面节奏。P0 测量后再定，可选：
- (a) 同步显示，帧率不固定（现状，修好 C1、C2 后约 25 fps）；
- (b) 同步显示，固定每帧停 3 个刷新周期（20 fps，节奏完全均匀）；
- (c) 摄像头实时 30 fps，光标和方块按速度外推到显示时刻（画面流畅，转向时可能略有超调）。

### 5.2 对齐

- 全部页面改用 flex 或 grid 布局，加 `lv_obj_align`，不再写死坐标；
- 统一间距和栅格，统一由 theme 中的常量给出；
- 游戏场景内部仍用坐标，安全区常量保持不变。

### 5.3 醒目文字

- 新增 Noto Sans SC Bold（OFL，与现有字体同源）子集：
  - 标题 32 / 48；
  - 数字 64 / 96：分数、倒计时、高度、fps。
- 强调用彩色胶囊标签（渐变底），关键数字用强调色加大号粗体。
- 弹出提示（"完美！""倒塌！"）用缩放动画；RND 支持缩放。
- 静态标题可以加文字阴影：用错位的第二个标签实现，不用软件模糊。

### 5.4 性能约束

LVGL 部件的样式越复杂，软件渲染越慢（benchmark 整屏平均 43 ms）。因此：
- 摄像头页和游戏页的动态区域只用简单样式；
- 复杂样式只放在静态区域；
- 每页给出绘制时间的实测值。

## 6. 积木塔：场景展现

### 6.1 画面（1280×720）

| 区域 | 内容 |
|---|---|
| 背景 | 镜像摄像头画面（L0）。L1 上铺一层静态半透明暗幕，让积木更突出，同时看得到自己的手（待定 D3） |
| 地面平台 | 画面下方居中，在安全区内 |
| 积木架 | 左右两侧各 3 格，显示待用积木的材质和形状，用完补充 |
| 高度尺 | 右侧。显示当前塔高（大号粗体数字）、本局最高线、目标线 |
| 顶栏 | 关卡、目标、倒计时条、分数、性能窗 |
| 手 | 张开或握拳的手形光标；在积木上握拳停留时显示 lv_arc 进度环 |
| 落点预览 | 拿着积木时，在下方画半透明投影 |

### 6.2 操作

1. **抓起**：在积木架或已落下的积木上握拳，即抓起。积木通过弹簧关节跟手，移动时有自然的摆动和惯性转动。
2. **旋转**：待定（D4），可选：
   - (a) 按手的倾角旋转，每 15° 一档；
   - (b) 用一个专门手势每次转 90°；
   - (c) 不能旋转，积木保持架上的方向。
3. **放下**：张开手后积木受重力下落，与其他积木碰撞、堆叠，可能倒塌。
4. **丢手**：丢手 ≤ 200 ms 时继续保持抓住状态，光标按速度外推；超过即视为松手（同时解决 C5 的断触感）。

### 6.3 积木

- **形状**：正方块、长条木板、短砖、三角（屋顶）、半圆拱、圆柱。拱用多个凸多边形组合。
- **材质**：

| 材质 | 密度 | 摩擦 | 弹性 | 特点和外观 |
|---|---|---|---|---|
| 木 | 中 | 高 | 低 | 木纹，最稳 |
| 石 | 高 | 高 | 低 | 很重，适合做底座 |
| 冰 | 中 | 很低 | 低 | 半透明，容易滑 |
| 金属 | 很高 | 中 | 低 | 拉丝金属，适合压顶 |
| 橡胶 | 低 | 高 | 高 | 会弹 |
| 玻璃（D5） | 中 | 中 | 低 | 半透明；撞击力超过阈值就碎，碎成粒子 |

### 6.4 物理

- 2D 刚体，**有转动**，因此可以倒塌（待定 D2）：
  - 冲量迭代求解，参考 Box2D-Lite 的结构自己实现；
  - 碰撞检测：凸多边形用分离轴，另有圆；
  - 摩擦、弹性、静止休眠。
- rv32im 没有 FPU，全部用 Q16.16 定点。
- 规模：60 Hz 步长，速度迭代 8 次，最多 24 块。估算每步 ≤ 2 ms（估算，P3 在主机上用指令计数实测）。

### 6.5 绘制

- RND 不支持旋转，积木按角度预先生成帧：
  - 每种积木 64 个角度（每档 5.6°）；对称形状按对称性减少；
  - 进入游戏时由 CPU 生成到 DDR，显示进度条；
  - 只生成本关用到的积木。
- 只有运动中的积木重绘，休眠的积木不重绘。
- 特效：落地扬尘粒子、玻璃碎片、高度破纪录时的弹出文字。

### 6.6 流程

1. **待机**：自动演示一座塔倒塌。
2. **教学**：抓一块积木放到平台上。
3. **挑战一"盖高楼"**：90 s 内达到目标高度，塔稳定 3 s 算成功。
4. **挑战二"地震测试"**：平台晃动 5 s，按剩下的高度计分。
5. **自由搭建**：积木不限，记录最高高度。
6. **结算**：显示高度、用时、星级。

### 6.7 美术

全部原创，由 Codex 生成，风格与现有游戏一致。
