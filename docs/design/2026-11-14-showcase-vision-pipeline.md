# showcase 视觉流水线页：检测、图像处理、几何变换任意组合

## 1. 背景和问题

- 现在的 showcase 把视觉功能分成三页：
  - 视觉识别：摄像头 → YOLO，检测框画在画面上；
  - 图片识别：PC 图片 → YOLO；
  - 图像处理：顺序固定为 摄像头 → PIX → GEO → 显示。
- 这三页都只是固定通路，看不出硬件"各引擎经 DDR 串联、顺序可以任意编排"的能力。
- 用户 2026-11-14 要求：把检测、图像处理、几何变换放进同一个功能页，体现任意组合，并规划好怎么展示。
- 硬件分析见 2026-11-13 的讨论（VIN CH1 因此保留，设计记录 `2026-11-13-soc-slim.md` 第 4 节）：
  - 现有硬件已经能做 DDR 串联：
    - 内存源 + CH0 = DDR → PIX → DDR；
    - 内存源 + CH2 = DDR → NPU 输入；
    - GEO、RND、NPU 本来就是 DDR 到 DDR；
    - CH1 把摄像头原图写进 DDR。
  - **只改软件，不改 RTL。**

## 2. 约束（硬件事实）

| 引擎 | 输入 → 输出 | 每帧耗时（1280×720） | 限制 |
|---|---|---:|---|
| VIN CH1 | 摄像头 → DDR 原图 | 随摄像头帧 | — |
| VIN CH0 + PIX | 摄像头或内存源 → DDR | 内存源：约 3.7 ms | PIX 内部顺序固定：点运算 1（亮度、对比度、伽马）→ S1 → S2 → 点运算 2（灰度、二值化、反色），见 pix-spec 1 |
| VIN CH2 | 摄像头或内存源 → NPU 输入 | 约 4 ms | 源必须是 1280×720（vin-spec 6，ERR 8） |
| 内存源 | DDR RGB565 → CH0 / CH2 | — | **只有一个**；同一帧可以同时送 CH0 和 CH2 |
| GEO | DDR RGB565 → DDR RGB565 | ≤16.7 ms（缩放 s≤1），≤33 ms（s≤2） | 只支持 RGB565 |
| RND | DDR → DDR：画框、贴图、把 ARGB 界面层混合进 RGB565 | 1280×720 混合：约 4 ms（估算） | — |
| NPU | INT8 输入 → 检测结果 | 约 35 ms | 一个；与其他引擎并行 |
| DISP | L0（RGB565 视频）+ L1（ARGB 界面），扫描时叠加 | — | 叠加结果不在 DDR 中 |

- **格式统一**：所有中间画面都用 1280×720 RGB565。GEO 输出也始终是 1280×720 的画布，缩放和旋转发生在画布内。因此任何一级的输出都可以接任何一级，检测也总能满足 CH2 的尺寸要求。
- **DDR 带宽**（估算，有效带宽未实测）：
  - 每多一级经 DDR 中转（读一帧、写一帧），30 fps 时约 110 MB/s；
  - 基础负载（显示、NPU、摄像头、CPU、LVGL）约 1.25–1.37 GB/s；
  - 规格规定的持续流量上限为 1.95 GB/s，所以中转级数约 5–6 级可以保持 30 fps。
- **流水线**：不同引擎可以同时处理不同的帧。帧率由最忙的那个引擎决定（比如内存源每帧的总占用、GEO 每帧的总占用），延迟是各级耗时之和。
- 每一级完成后，必须在中断里立即启动下一级（同 T-VIS-ISR 的做法）。如果交给协作式调度去启动，每级都可能多等 20–35 ms。

## 3. 方案：积木链

### 3.1 用户看到的模型

页面上是一条从左到右的**积木链**：

```
[来源] → [积木 1] → [积木 2] → … → [积木 n] → [HDMI]
```

- **来源**：摄像头；PC 图片（取代图片识别页）；测试图（存在 DDR 中）。
- **积木**（每块都可以带参数）：

| 积木 | 参数 | 对应硬件 |
|---|---|---|
| 亮度/对比度、伽马 | 数值 | PIX 点运算 1 |
| 滤波 | 均值 / 高斯 / 锐化 / Sobel / 腐蚀 / 膨胀 | PIX S1 或 S2 |
| 灰度、二值化（阈值）、反色 | — / 阈值 | PIX 点运算 2 |
| 几何 | 角度、缩放、平移、水平/垂直镜像 | GEO |
| 检测 | 置信度阈值、类别 | VIN CH2 + NPU |
| 叠加 | 叠加检测框 / 叠加界面 | RND |

- **积木可以任意排列、重复使用**。滤波可以放 3 级以上，几何变换可以放在 PIX 之前或之后，检测可以放在任何位置。
- **检测是"取样点"**：NPU 看到的是这一位置的画面，画面原样继续往下传。框的坐标属于这一位置。
- **叠加**放在检测之后、几何之前，框会跟着画面一起旋转。例如"摄像头 → 检测 → 叠加（框 + 界面）→ 旋转 → HDMI"：视频、检测框、LVGL 界面合成后整体旋转缩放，正是用户提出的场景。
- **叠加**放在几何之后：框的坐标经同一个仿射变换映射。90° 的倍数、缩放、平移下框仍是矩形；任意角度下画成外接矩形，界面上会注明。
- 限制只有三条，界面上直接说明原因：
  1. 检测最多 1 块，因为 NPU 只有一个；
  2. 积木最多 8 块；
  3. 超出 DDR 或引擎预算时帧率会下降，下降多少由预算条实时显示。

### 3.2 编译成硬件执行序列

软件把积木链编译成一串**跳**，每一跳是一个引擎完成一次 DDR 到 DDR 的处理：

1. 摄像头入口：
   - 默认摄像头 → CH1 → DDR 原图。
   - **融合**：如果链首的连续 PIX 积木符合 PIX 的固定顺序，就直接走 摄像头 → CH0（PIX）→ DDR，省掉一跳。界面上用"融合"标记。
2. 连续的 PIX 积木中，符合固定顺序的一段合成一次 PIX 处理（内存源 → CH0）。不符合顺序的地方，拆成下一次处理。
   - 例：高斯 → 灰度 → 高斯，拆成两次：(S1 高斯, 灰度) 和 (S1 高斯)。
3. 几何：一块积木就是一次 GEO。
4. 检测：内存源 → CH2 → NPU。
   - 如果检测前一跳是内存源 → CH0，就让内存源同一帧同时送 CH0 和 CH2，不多占一次内存源。
   - NPU 自己按约 28 fps 取最新的一帧，不阻塞主链。
5. 叠加：一次 RND。框用最近一次的检测结果，界面上显示框的滞后时间。
6. 最后一跳的输出给 DISP L0。叠加里选了"叠加界面"时隐藏 L1，避免界面显示两遍。

### 3.3 执行

- 每一跳有 3 块缓冲（每块 1.84 MB），处理时总是取最新的一帧，跟不上时丢旧帧。帧号沿用 VIN 的 frame_id。
- 每一跳完成时，在中断里启动下一跳，代码沿用 `vision.c` 的中断重启和所有权划分。
- 共享引擎排队：内存源、GEO、RND 各一个队列，按帧号先后执行。
- 测量：
  - 每一跳的开始、结束时间（mtime）；
  - 每个引擎的占用率；
  - 端到端延迟：从 VIN 帧完成中断到包含该帧的 DISP 翻页，口径与 P5 设计 8.6 节相同；摄像头入口跳的耗时记为 0，界面显示"随摄像头帧"；
  - 各 DDR 端口的读写字节和等待（xbar 计数器，卡 68 已保留）。

## 6. 决策（用户 2026-11-14）

- 视觉识别、图片识别、图像处理三页合并为"视觉流水线"一页，采用积木链加预设的方式。
- 下面的规则由协调者确定：
  - 积木最多 8 块，检测最多 1 块；
  - 链首能融合的就融合；
  - 叠加放在几何之后时，框按仿射变换映射，任意角度画外接矩形；
  - PC 工具可以编辑积木链。

## 7. 冻结接口（PIPE-SPEC，2026-11-14）

### 7.1 积木链数据（板端、UI、PC 共用，小端）

链块 100 B：

| 偏移 | 字段 | 类型 | 含义 |
|---|---|---|---|
| 0 | `source` | u8 | 0 摄像头，1 PC 图片，2 测试图 |
| 1 | `count` | u8 | 积木数，0–8 |
| 2 | `view` | u8 | 主画面显示第几块积木的输出（0 起）；0xFF 为最终输出；0xFE 为来源原图（取代原图像处理页的"原图"开关） |
| 3 | `preset` | u8 | 0 自定义，1–8 对应 4.1 节预设表的顺序；任何修改都会把它置 0 |
| 4 + 12k | 积木 k | 12 B | 见下表；`k ≥ count` 的积木全为 0 |

积木 12 B：`type`(u8) + `flags`(u8) + `p[5]`(5 × i16)

| type | 积木 | flags | p0 | p1 | p2 | p3 | p4 |
|---|---|---|---|---|---|---|---|
| 1 | 亮度/对比度 | 0 | brightness −256…255 | contrast Q8 0…512 | 0 | 0 | 0 |
| 2 | 伽马 | 0 | gamma_tenths 3…30 | 0 | 0 | 0 | 0 |
| 3 | 滤波 | 0 | op 1…6：均值、高斯、锐化、Sobel、腐蚀、膨胀 | 0 | 0 | 0 | 0 |
| 4 | 灰度 | 0 | 0 | 0 | 0 | 0 | 0 |
| 5 | 二值化 | 0 | threshold 0…255 | 0 | 0 | 0 | 0 |
| 6 | 反色 | 0 | 0 | 0 | 0 | 0 | 0 |
| 7 | 几何 | bit0 水平镜像，bit1 垂直镜像 | angle −180…180 | scale_percent 50…400 | translate_x −1280…1280 | translate_y −720…720 | 0 |
| 8 | 检测 | 0 | 0 | 0 | 0 | 0 | 0 |
| 9 | 叠加 | bit0 检测框，bit1 界面 | 0 | 0 | 0 | 0 | 0 |

- 检测的门槛和类别沿用 DETECT（8.2 节 0x07），对整条链生效。
- 合法性规则（板端检查；不合法时整组拒绝，原链不变）：
  1. `count` ≤ 8，各字段在表中范围内，未用字段为 0；
  2. 检测最多 1 块；
  3. 叠加的 bit0 只能在其前面有检测时置位；
  4. 叠加的 flags 不为 0；
  5. `view` < `count`、`view` = 0xFF 或 `view` = 0xFE。
- 错误码沿用 8.1 节：长度不符 1，格式或范围不符 2。

### 7.2 UI 接口（`ui_data.h`，以头文件中的声明为准）

```c
enum { UI_BLOCK_MAX = 8 };
typedef struct { uint8_t type, flags; int16_t p[5]; } ui_block_t;
typedef struct { uint8_t source, count, view, preset; ui_block_t block[UI_BLOCK_MAX]; } ui_chain_t;
ui_chain_t ui_data_chain(void);
/* 0 = accepted, else 8.1 error code; rejected chains leave the current one unchanged. */
unsigned ui_data_chain_set(const ui_chain_t *chain);
void ui_data_chain_preset(unsigned preset);              /* 1..8 */
typedef struct {
    uint8_t engine;          /* 0 CAM-CH0/PIX fused, 1 CAM-CH1, 2 MEMSRC-CH0/PIX,
                                3 MEMSRC-CH2/NPU, 4 GEO, 5 RND overlay */
    uint8_t first, last;     /* block range served by this hop */
    uint32_t us;             /* measured average duration over the last second */
} ui_hop_t;
typedef struct {
    unsigned hop_count; ui_hop_t hop[12];
    unsigned fps, e2e_us, box_lag_us, npu_us;
    unsigned ddr_mbps, ddr_limit_mbps;      /* limit = 1950 */
} ui_pipe_stats_t;
ui_pipe_stats_t ui_data_pipe_stats(void);
/* 160x90 RGB565 thumbnail of block k's output, refreshed at 5 fps; k = 0xFF is the source. */
const lv_image_dsc_t *ui_data_thumb(unsigned block);
```

- `ui_app_t` 中，`UI_APP_CAMERA` 改名为 `UI_APP_PIPELINE`，值 1，删除 `UI_APP_IMAGE` 和 `UI_APP_PROCESS`。值 2、3 保留不用。
- `ui_vision_t` 继续提供检测结果和 PC 图片信息。
- 以下接口全部删除：`ui_process_config_t`、`ui_data_process*`、`UI_PROC_*`。

### 7.3 EDSC（8.2 节的修改）

- `app` = 1 为视觉流水线，2 和 3 不再使用。图片的 BULK_BEGIN 只在 `app` = 1、`source` = 1 且状态为 RUNNING 时接受。
- 删除 0x06 PROCESS。STATE payload 偏移 20 的 24 B 改为：`chain_rev`(u32，每次链变化加 1) + 20 字节 0。
- 新增：

| type | 方向 | payload | 说明 |
|---|---|---|---|
| 0x09 CHAIN | PC → 板 | 7.1 节链块，100 B | 整组替换。合法时下一帧生效，回复 ACK(2)；否则回复 ACK(3, error)，原链不变 |
| 0x0A PRESET | PC → 板 | `preset`(u8，1–8) + 3 字节 0 | 回复 ACK(2) |
| 0x88 CHAIN_STATE | 板 → PC | `chain_rev`(u32) + 7.1 节链块 | HELLO 之后、链变化时发送 |
| 0x89 PIPE_STATS | 板 → PC | `fps`, `e2e_us`, `box_lag_us`, `npu_us`, `ddr_mbps`(5 × u32) + `hop_count`(u8) + 3 字节 0 + `hop_count` × (`engine`, `first`, `last`, 0 各 u8 + `us` u32) | `app` = 1 且 RUNNING 时每 1 s 发送 |

### 7.4 编译规则（板端；主机测试覆盖）

1. 来源为摄像头，且链首有连续的 PIX 积木符合 PIX 固定顺序（pix-spec 1）时，链首这段与摄像头融合，走 CAM-CH0/PIX；否则先走 CAM-CH1。
2. 其余连续的 PIX 积木，按固定顺序尽量合并成一次 MEMSRC-CH0/PIX。滤波按 S1、S2 两个槽计数，同一种滤波连用两次也可以在同一次里；第三块滤波开始下一次。亮度/对比度、伽马、灰度、二值化、反色各只有一个，重复出现时开始下一次。顺序倒退处（例如灰度之后接滤波）也开始下一次。
3. 几何：每块一次 GEO；叠加：每块一次 RND。
4. 检测：如果检测的输入就是下一次 MEMSRC-CH0 处理的输入，这一帧内存源同时送 CH0 和 CH2；否则单独一次 MEMSRC-CH2。NPU 按最新帧异步运行。
5. 来源为 PC 图片或测试图时，第一跳的输入是该图片所在的 DDR 缓冲。
6. 最后一跳的输出接 DISP L0。叠加 bit1（界面）置位时隐藏 L1。
