# CPU v2 与周期模型的逐结构性能对齐

## 条件与复现

- RTL 和模型实现快照：`30d4805a56b027ac50a9c620be3ceb5e80265fa6`；NONE，ISSUE_WIDTH=1/2。没有修改 RTL、技术包装、既有测试或模型。
- 工具：GCC 15.2.0，Spike 1.1.1-dev，Verilator 5.051 devel（v5.050-99-gf8fb1d664）。此为周期仿真，不是 FPGA 频率/资源测量；器件、速度等级与时序约束不适用。
- 主表模型为任务引用的原始无限完成窗口：W1 `BASES['small']`，W2 `BASES['full'] + combo4-zba`；保留 IcacheProbe(1)、寄存前端余量、实际操作数的 C07 DIV 日程。协调者已确认主表用 completion_entries=0；N4 单独诊断，不替换主表或修改默认值。后续 `cf8604e4f` 恢复了同一原始默认口径。
- 38 个汇编微基准，每个 payload 重复 64 次；同一个 kernel 先完整执行一次，再执行计时调用。标记与尾部的可能错路取指行也先执行预热。数据只在一条热 D$ 行内；store 的最终内存值在窗口后由软件检查。
- 所有实现消费同一 ELF/指令编码；v2 用真实 I$/D$ 和原 AXI64 BFM，旧竞赛核用 `verif/block/cpu/b1` 原有零 miss 缓存接口模型。旧核列是第二参照，其缓存实现与 v2 不同。
- RTL 在地址零执行两条复位跳板，Spike 从同一 ELF 的 DDR 入口开始（安装的 Spike debug module 占据地址零）。寄存器/PC 对照从 ELF 入口开始；整个预热与计时指令流相同。计时是 start_time 首指令退休到 stop_time 首指令退休，不扣调用/返回开销。
- 原始数据：`build/cpu2-conformance/cycles.json`、各例 `coremark.elf`、`numeric.dis`、`spike.log`、`model_w{1,2}[_n4].json`、`w{1,2}.csv`、三套 RTL 的 `.log/.trace`。CSV 在 posedge 的 NBA 更新前采样，valid/ready 表示该沿接受；cycle 为十进制，其他列为十六进制。以下代码行均按上述快照编号；`lsu.v` 等简称指 `rtl/cpu2/edrv32_cpu2_<简称>.v`，模型脚本位于 `tools/cpu/eval/`。

在该冻结源树中叠加本任务新增文件，仿真环境运行：

```sh
/usr/bin/python3 tools/cpu/run_model_conformance.py build
/usr/bin/python3 tools/cpu/run_model_conformance.py run
/usr/bin/python3 tools/cpu/run_model_conformance.py lint
/usr/bin/python3 tools/check/verilog_style.py rtl/cpu2/*.v
```

可用 `--names load_stream load_use` 复跑单项。三套 RTL 全部执行至 tohost 并与 Spike 比较 PC、编码、rd、整数结果；store 测试另在软件中核对最终数据。没有把内部信号当成架构期望。

## 缺陷与结构差距（按单项微基准可恢复拍数排序）

收益均为**估算**：由已证实的稳态日程计算，未修改 RTL 做反事实测量。不同例的数字不能相加成 CoreMark 收益；同一例的窗口、LSU、依赖成本也会重叠。分类 a 表示实现未达到规格的规定日程，b 表示冻结结构/规格缺口使原模型的日程不能成立；b 需要用户选择新的实现契约，不能由 worker 擅改模型掩盖。

| 编号 | 已确认现象与根因 | 类别 | 建议修法 | 单项预计收益 |
|---|---|---|---|---|
| D01 | store 的准备、完成捕获、队头授权、done/退休占据同一个 LSU 事务槽；下条 store 不能提前准备 | b | 将可缓存 store 的准备流水与队头副作用授权分开，利用按 tag 的待提交记录；保留不可撤销副作用顺序，明确准备与授权各自 II | 先预备流水化 II4→II2 约256拍；若重订可缓存写缓冲接受即退休的边界，II1 上限约384拍。N4 成本不重复计入 |
| D02 | W1 RTL BTB 是 64 个 4B 字槽，原模型是 64 个 8B 组并含控制位置；8B 间隔的 64 条 JAL 在 RTL 只使用 32 个索引、相互驱逐 | b（规格几何缺口，修法待定） | 明确“项”的覆盖跨度/位置，恢复 64 组加位置语义，或重新决定等效容量；不能只沿用“64项”这个数字 | 热 JAL 例约 256 拍上限；覆盖跨度变化，不是缓存 miss |
| D03 | 注册重定向拍停止取指，下一拍 F1，再 F2、IB、ID/EX；相同误预测数量下比模型每次多约 2 拍 | b | 用已经寄存的恢复 PC 在恢复拍发起目标 F1，重新安排 F2/IB/ID 捕获边界；同步定义取消沿新请求的归属 | 66 次误预测约 132 拍；taken/JALR/晚分支例都重复出现 |
| D04 | `lsu.v:257` 仅 IDLE ready；热 load 完成的 RESPONSE 拍不能接下一条，实际 II2 | a | I05b 所在工作项：登记足够容量，允许完成与下一条接受重叠，并使 early 查询与真正下一拍请求关联 | 128 条 load 的 127 个间隔可省约 127 拍 |
| D05 | MUL 请求到完成接受5拍，相关 MUL 请求/EX间隔6拍；规格消费者间隔4，问题在核级交付/消费边界 | a | 重排最后一级结果交付、issue 源捕获与首乘法级，让已寄存结果按规定间隔供消费者；保持本地背压，不能只改延迟常数 | 64 条相关 MUL 的 63 个间隔从 6→4：约 126 拍；独立流另受 N4 限制 |
| D06 | NONE 四项完成记录，先捕获 done 再退休，释放信用只在下一拍可用，纯双 ALU 变为“2、2、0”条/拍 | b | M01 已量化；用户决定完成容量或信用循环/捕获退休边界，不能擅自增参数或改模型默认值 | 256 条独立 ALU：稳态 192→128，约 64 拍 |
| D07 | 单发射合格 load 的 early hit 已经成功，但只能等普通完成才给 ID 源；消费者 EX 间隔为 2 而模型短 load 为 1 | b | 明确单发射短 load 的真实捕获日程；重排提前查询/本地捕获使 ID 看见寄存结果。仅接通双发射晚执行的 early_resp 不能实现 W1 的 1 拍短 load | 64 组 load-use：约 64 拍；不能与 D04 对同一等待重复计益 |
| D08 | CSR 每条必须等 credit=N；分配→请求→完成→退休→下一条分配，稳态 II4，模型/旧核 II3 | b | 把 CSR 请求接受与有序分配捕获对齐，或明确允许读取在已提交边界预备；保持写 CSR 原子性和串行规则 | 64 条 CSR 的 63 个间隔约省 63 拍 |

只有以上 8 项被本轮证据支持为独立根因，没有为了凑满“前10项”拆分同一等待。后文给出每项逐拍证据、模块行号和其余结构的排除结果。

### D01：store 单事务槽把整个提交往返串行化

### D02：BTB 的“项”不是相同的地址覆盖单位

证据位置：`predictor.v:327-333` 的 W1 read/write 地址为 PC[7:2]、tag 为 PC[31:8]；双读副本不增加逻辑容量。模型 `pipe_model.py:119,124,152` 用 `group_bytes` 决定索引，W1 group_bytes=8，所以是 PC>>3 的 64 组。W2 设置 unaligned_fetch 后模型也是按字索引，不能把 W1 的差异套到 W2。

例如同一热 JAL 流中的两个真实 PC：

| PC | RTL W1 PC[7:2] / tag | 模型 (PC>>3)&63 |
|---|---|---:|
| 0x80000060 | 0x18 / 0x800000 | 0x0c |
| 0x80000160 | 0x18 / 0x800001 | 0x2c |

`jal/w1.csv` 的计时窗口有66次执行重定向，模型同一窗口的 control_misses=4。`jal` 的 kernel 是 64 条间隔 8B 的直接跳转，I$ 已热，RTL W1 每次使用的索引在 32 条后重用，tag 不同；第二遍仍持续冲突。CSV 可见每条热 JAL 的执行恢复，不是对冷代码的推测。`branch_taken` W1 同样受 BTB 几何影响；方向预测还受一遍预热的历史状态影响，不能把全部分支差距都算为 BTB。

### D05：MUL 的结果级与消费边界

根因位置：`mul.v:94,101,134,143-155`：valid[3] 还要 push 到 count_r 控制的本地结果槽，下一拍才产生 complete_valid；`issue.v:679-681,942-948,1648-1652,1906` 完成旁路在分配时捕获，真正的下一条 MUL 请求随后由 pending 项交付。当前核级日程不能达到 CPU5.2 的 MUL 消费者 EX 间隔4。

## 其余结构与差距解释

- ALU 相关链、移位相关链：稳态1条/拍，未发现额外 EX 延迟。W2 连续相关简单 ALU 能进入晚执行；不是所有 RAW 都被禁止配对。
- C01：A+L/L+A、A+M/M+A、A+B/B+A、B+M/M+B、B+L/L+B、L+M/M+L、A+D/D+A 均通过同一 ELF 的架构对照。CSV 可见合法双分配以及 LSU 管线互换；持续少配主要归于信用、单 LSU 和乘法结果驻留，不据平均 IPC 指控矩阵错误。
- 重复源码中的相邻两条并不强制是同一个发射组：A+L/A+M/B+M/B+L/L+M/A+D 例中，各有2次期望方向配对，之后因窗口/入口限流发生相位移动，出现61次反向跨迭代配对；各反向专例有64次同方向配对。`late_AA` 只出现2条真正 late，不能独自证明晚执行上限；`alu_chain` 有128条 late，`ordinary_load_use` 有32条 late，后两者确认了实际晚执行路径。
- 普通 load→晚消费者、提前 AGU 不合格：`ordinary_load_use` 与 `agu_ineligible` 的结果均正确；不合格例不产生 early 查询。N4 模型的部分例甚至比 RTL 慢，说明此诊断不是精确到拍的 oracle，不把其正负残差全列为 RTL 缺陷。
- DIV：输入 0x12345678/7，k=27，正常日程 W1 L=30、W2 L=17；除零 L=2。请求间隔与 C07 一致，RTL 相对原模型只剩短窗口入口/返回成本，没有再发现每次迭代的额外拍。A+D 与 D+A 的 W1 有时快于模型，不是错误。
- 条件不跳、JAL/JALR 与 call-return：没有结果错误。预测预热只执行一遍，不承诺所有方向表已经收敛；具体 mispredict 数必须连同周期一起比较。旧核 call-return 例较慢，也说明旧核不是所有结构的共同上限。
- 边界差异：表内含两条调用/返回控制；少量误预测与 start/stop 同周期双退休差异会留下约几拍的固定差。不能把 `shift_chain` 等短例的几拍差全部宣称为每条指令的性能缺陷。
- HPM 观察口径：原 tb 的 `HPM event=4` 是逐拍 hpm_event_w[3] 观察，而 CPU CSR 的“退休控制条数”走独立 hpm_branch_count。不能把该日志的0当成没有分支；本报告的控制数来自 trace/恢复事件。此为观察口径，未列成有性能收益的缺陷。
